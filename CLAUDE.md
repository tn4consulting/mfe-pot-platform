# mfe-pot-platform — Government of Canada MFE Proof of Technology

## What this is

A proof-of-technology (PoT) demonstrating Angular micro-frontend (MFE) architecture, following Government of Canada design/accessibility/bilingual standards. It is framed around a fictional ESDC "you lost your job" scenario — a citizen-facing shell branded as a mock of **"My Service Canada Account" (MSCA)** aggregating four independently-built MFEs — but **this is fictional scaffolding to give the architecture real shape, not a production build**. GC design, accessibility, and bilingual standards are followed faithfully because proving those out *is* the point of the exercise. Authentication and citizen data are intentionally mocked/simplified: there is no real IdP, no real PII, no compliance/security hardening in scope.

**This repo is the platform repo of a 6-repo split** — it started as a single Nx monorepo containing all 5 frontends and has since been carved into 6 independent repos (the split is done; see "Monorepo → per-app repos" below for how and "Not yet built" for what's left in the surrounding hosting/CI work). This repo now holds only what's genuinely shared or has no single frontend owner: `libs/shared/*` (published as `@tn4consulting/shared-*` packages), the `client-profile-service` BFF, the composed `mfe-e2e` suite, Strapi, and the two Helm library charts. The 5 frontends (plus their own dedicated BFFs) live in their own sibling repos. **This file remains the durable architecture reference for the whole family** — the sibling repos' own `CLAUDE.md` files point back here for rationale rather than duplicating it, so keep this file accurate for the family as a whole, not just this repo's own directory contents; where a section describes code that now lives in a sibling repo, that's noted inline. See `../CLAUDE.md` (the `mfe-pot` meta repo one level up) for the full repo map and cross-repo mechanics.

Full design rationale lives in `docs/plans/` (see `mfe-pot-initial-design.md` for the initial design, kept updated with an "Updates Since Initial Approval" section as decisions evolve, and `20260801-1935-mfe-pot-polyrepo-split-and-k8s-hosting.md` for the full history of the split itself). This file is the durable, living summary — update it when architecture decisions change; don't let it drift from what the code actually does.

## Tooling

Runtime versions are managed with **asdf** (`.tool-versions` at repo root pins `nodejs`). If you hit a `require() of ES Module ... not supported` error from a toolchain package, check the Node version first — several build-time dependencies (e.g. `@angular/compiler-cli`, `magic-string`) ship ESM-only builds that need Node's unflagged `require(esm)` support (Node ≥ 22.12), not just any Node 22.x. Package manager is **pnpm** (not asdf-managed; installed globally/via corepack). Local CMS/registry infra (Strapi) runs on the local `kind` cluster via its own Helm chart (`charts/strapi`, deployed with `pnpm deploy:local`) — needs Docker (for `kind`) running; see "Local CMS / federation directory: Strapi" below.

**Zoneless testing gotcha**: every app in this family uses Angular's zoneless change detection, and `fixture.whenStable()` does **not** wait for a plain `fetch()`/promise chain inside a lifecycle hook — it only tracks Angular-native pending work (signals, effects, the `PendingTasks` service), not arbitrary async code. If a component fetches data in `ngOnInit`, don't rely on `whenStable()` in its tests: `await fixture.componentInstance.ngOnInit()` directly, then call `fixture.detectChanges()` to force the render pass. See the sibling `mfe-pot-dashboard` repo's `apps/dashboard/src/app/app.spec.ts` for the pattern (dashboard's app component is the reference example — it no longer lives in this repo, see "The apps" below).

**`fileReplacements` only swaps TS module imports, not copied assets.** It works for environment.ts-style files (`apps/*/src/environments/environment.ts` → `environment.prod.ts`, wired per-app in `project.json`'s production config) but silently does nothing for files under `public/` copied via the `assets` glob — that's why the hosted federation manifest needs the separate `build-hosted` copy-step target instead (see Hosting section below).

**Vite/esbuild specially recognizes `new URL('...', import.meta.url)` and rewrites it for asset bundling** — even in dev mode, and even when the intent is just "compute my own serving origin" (needed so a federated remote's Transloco/asset requests resolve against its own origin, not the shell's). The rewrite hijacks the computation, producing a bogus `/@fs/.../vite-root/<app>` disk path instead of the real dev-server URL. Fix: split it across two statements — `const moduleUrl = import.meta.url; const assetBaseUrl = new URL('.', moduleUrl).href;` — the special-casing only triggers on the exact inline single-expression pattern. See `apps/shell/src/app/app.config.ts` and every remote's `remote-providers.ts`.

**Bare-specifier workspace libraries can't be imported from an app's own entry (`main.ts`).** Same root cause as the native-federation-sharing chicken-and-egg problem: `main.ts` runs before Native Federation's import-map/shared scope exists, and under `shimMode` *any* bare (non-relative) specifier resolves through that import map — including plain internal libraries that were never marked `shared`. It works fine everywhere else (anything reached via a lazy route or an exposed federated module, e.g. `apps/dashboard/src/app/app.ts` importing `shared-content-client`), just not in `main.ts` itself. `apps/shell/src/main.ts` inlines the small amount of fetch logic it needs rather than importing `shared-remote-registry`, for exactly this reason.

## The apps

The 5 frontends now live in their own repos, each with its own `CLAUDE.md` pointing back here for shared rationale:

- **`mfe-pot-shell`** — host app, branded MSCA: app frame, GC header/footer, language switcher, mock Sign-In-Canada-style login, runtime federation manifest reader. No BFF of its own.
- **`mfe-pot-dashboard`**, branded **MSCA-D** — 360° cross-benefit overview (eligible benefits, active applications, "my tasks"), payment history, correspondence, "tell us once" profile maintenance. Owns `dashboard-bff`.
- **`mfe-pot-job-bank`** — job search and apply. Owns `job-bank-bff`.
- **`mfe-pot-employment-insurance`** — EI application, claim status, EI reporting. Owns `employment-insurance-bff`.
- **`mfe-pot-employment-life-events`** — client-centric "you lost your job" guided journey stitching the other three together. No BFF of its own.

**What actually stays in this repo**: `libs/shared/*` (published as `@tn4consulting/shared-*` packages — auth, i18n, ui-gcds, content-client, remote-registry, federation-runtime, federation-config, runtime-config), the `client-profile-service` BFF (no single frontend owner, see "Backends" below), the composed `apps/mfe-e2e` Playwright suite, `tools/cms/strapi`, and the two Helm library charts (`charts/mfe-frontend-lib`, `charts/mfe-backend-lib`). Everything else described below (federation patterns, GCDS usage, i18n, security, BFF contracts) is the shared architecture every app repo follows — the actual source for most of it now lives in the sibling repos, not here.

## Non-negotiable requirements

- **Bilingual**: English and Canadian French everywhere the citizen sees it — UI chrome and CMS content. Contributor/process documentation (`docs/`) is **English-only** by explicit decision — not a GC citizen-facing surface, so it doesn't carry the bilingual requirement the product UI does.
- **Accessibility**: WCAG 2.2 AA, verified by automated tooling (axe), not just manual review or documentation.
- **GC Design System** (`@gcds-core/components` + Angular wrapper `@gcds-core/components-angular` — the `@cdssnc/gcds-components*` packages are deprecated/renamed) for all UI.
- **Docs kept current** in `docs/` (English-only — see the bilingual note above). `docs/plans/` holds process/planning history rather than reference docs — see "Planning documents" below.
- **Unit tests** (Jest) and **integration tests** (Playwright, run locally against local stubs/emulators — MSW, a local Strapi container, local BFFs) are required. No dependency on real external services for tests.
- **Angular** is the preferred framework.
- **TypeScript everywhere** — the Angular apps/libs and the BFF/service apps alike.
- Each MFE is **independently buildable, testable, and deployable**, and is **loaded dynamically at runtime** as a federated remote — never compiled into the shell at build time.

## Core architecture decisions

### Monorepo → per-app repos (done)
This repo split into 6: this one is the **platform repo** (`libs/shared/*` published as versioned packages, the shared `client-profile-service` BFF, the composed `mfe-e2e` suite, Strapi, the two Helm library charts) plus 5 per-app repos under `tn4consulting` — `mfe-pot-shell`, `mfe-pot-dashboard` (+ `dashboard-bff`), `mfe-pot-job-bank` (+ `job-bank-bff`), `mfe-pot-employment-insurance` (+ `employment-insurance-bff`), `mfe-pot-employment-life-events`. BFFs moved with whichever frontend owns them; `client-profile-service` has no single owner and stayed in the platform repo. Local multi-repo dev is **independent sibling clones tied together with a VSCode multi-root workspace file** (`../mfe-pot.code-workspace`) — deliberately not git submodules, because `git worktree add` doesn't auto-init submodule content and this environment's own subagent worktree isolation would silently see empty app directories.

Each extraction (job-bank first, then employment-insurance, dashboard, shell, employment-life-events) surfaced its own gotcha — worth knowing before touching any app repo's build/publish setup:
- **Published `@tn4consulting/shared-*` packages are ESM (`dist/index.js` uses `export *`) with no `"type": "module"` in their `package.json`**, so Jest's default CJS `require()` can't parse them once resolved through a real `node_modules` (the platform repo itself never hit this — its bare specifiers resolve straight to workspace TS source via `tsconfig.base.json` paths). Every app repo's `jest.config.cts` that imports one of these packages needs `@tn4consulting` added to `transformIgnorePatterns`'s negative-lookahead, the same fix already used for `@angular-architects`/`@softarc`/`@gcds-core`/`@jsverse`.
- **`pnpm install` inside a Docker build has no access to the host's `~/.npmrc`**, so it 401s fetching `@tn4consulting/*` from GitHub Packages — fixed with a checked-in `.npmrc` (`@tn4consulting:registry=...` + `${NODE_AUTH_TOKEN}` substitution) plus a BuildKit file-mounted secret (`--mount=type=secret,id=npm_token`, read via `cat /run/secrets/npm_token` — this environment's Docker Desktop doesn't support the newer `env=` mount form). CI passes its own `GITHUB_TOKEN` as the same secret.
- **`nx`'s postinstall script can hang indefinitely inside a Docker build** despite its own internal 30s watchdog `setTimeout` — root cause not fully isolated (something upstream of the script's own logic never gets far enough to hit the watchdog). Fixed by removing `"nx"` from `package.json`'s `pnpm.onlyBuiltDependencies` entirely; `nx`'s CLI doesn't need the postinstall hook to function.
- **TypeScript's implicit `@types` auto-inclusion can silently fail to pick up `@types/node`** when `ts-node` compiles `jest.config.cts` via a `tsconfig.json` that doesn't explicitly set `"types"` (root cause not fully isolated — likely an interaction between TS's auto-inclusion and pnpm's symlinked `node_modules/@types` layout under `moduleResolution: "bundler"`). Fixed defensively in every app repo's `tsconfig.base.json`: `"types": ["node"]`, explicit rather than relied-on-implicitly.
- **A missing `.tool-versions`/`pnpm-workspace.yaml` in a freshly-extracted repo silently falls back to the wrong Node version**, reproducing the exact `"require() of ES Module ... not supported"` error this file documents as a Node<22.12 symptom — a real error message pointing at the wrong root cause. Check both files exist and are correct before chasing an ESM/native-federation theory.
- **`federation.config.mjs`'s `exposes` map needs checking on any app that exposes something beyond its own root component** (only dashboard does today, via `./PaymentHistoryWidget`) — a stale nested `libs/<domain>/...` path left over from flattening `libs/` fails the build with `FsPath ... does not exist`, since only the app-entry expose path gets touched by the usual extraction steps.
- **A published Angular-component library (only `shared-ui-gcds` today) needs ng-packagr, not the workspace's default tsc build**, to publish real Ivy metadata — a downstream app's AOT/production build fails with `NG3004`/`NG2012` against a plain-`tsc`-built package even though the same source builds fine in-workspace. Fixed by giving `shared-ui-gcds` its own `@nx/angular:package` build target (`angularCompilationMode: "partial"`, its own dependencies moved to `peerDependencies` since ng-packagr refuses non-peer deps), and teaching `publish-shared-lib.mjs` to detect ng-packagr libs (presence of `ng-package.json`) and publish straight from their self-contained `dist/` output.

`@nx/enforce-module-boundaries`'s dep constraints were tightened from a wide-open `sourceTag: '*' -> onlyDependOnLibsWithTags: ['*']` (which didn't actually restrict anything) to real per-scope rules, specifically *before* extracting any app repo — while a violation is still a one-PR fix, not a cross-repo rewrite. This caught a real one: `apps/shell` had a compile-time import of an `employment-life-events`-scoped lib (`PAYMENT_HISTORY_WIDGET_LOADER`), which can't work once they're separate repos — see "Strong contracts" below for the fix.

**Hosting moved from Firebase to Kubernetes (AKS + local k8s via kind), deployed via Helm; `docker-compose.yml` has been removed**, replaced by `charts/strapi` deployed to the local `kind` cluster (see "Local CMS / federation directory: Strapi" below). The prerequisite runtime-config migration (build-time `environment.ts`/`fileReplacements` → a container-injected `window.__mfePotEnv` read at startup) has landed — see "Hosting: Kubernetes + Helm" below for the full mechanism. Still open: AKS/ACR access from CI — deferred until the whole pattern is validated against a local `kind` cluster first.

### Strong contracts between split repos
Versioned npm packages are the actual mechanism, published from the platform repo to GitHub Packages under the `@tn4consulting` scope (GitHub Packages requires the npm scope to match the owning org):
- **`libs/shared/*` ships as `@tn4consulting/shared-<name>`** (auth, i18n, ui-gcds, content-client, remote-registry, federation-runtime), each with its own `package.json`, built `.d.ts`, and independent version. A breaking change requires a major bump; a consumer that hasn't updated simply fails to build — that's the enforcement, not a convention someone has to remember.
- **`libs/shared/federation-config`** (plain JS, no build step — see below) holds the Native Federation `shared`/`skip`/`features` block every app's `federation.config.mjs` imports instead of hand-copying. Before this existed, all 5 apps carried an identical, independently-editable copy of the singleton version-pinning config — fine in one repo/one PR, but exactly how federation singleton mismatches happen silently once 5 repos can each drift it independently.
- **`payment-history-widget-loader.token.ts` lives in `shared-federation-runtime`**, not in `employment-life-events`'s own feature library where it used to live — that was the module-boundary violation above. Both the shell repo (which provides the token's value) and the employment-life-events repo (which injects it) now depend on the same published package instead of one repo importing the other's source.
- **`platform-versions.json`** (repo root) is the single checked-in source of truth for the Angular/RxJS/GCDS/Node/TypeScript versions every app repo must stay aligned on — required because Native Federation's shared-singleton contract silently breaks at runtime (no compile-time warning across repos) if one app drifts its Angular version relative to the others. A future version-alignment check can read each deployed remote's live `remoteEntry.json` (which already lists every shared package's exact resolved version) and each BFF's `/health`, and assert they all agree with this file.
- **`default.json`** (repo root) is the shared Renovate preset every app repo's `renovate.json` extends (`github>tn4consulting/mfe-pot-platform`) — groups `@angular/*`, `@angular-devkit/*`, `@schematics/angular`, and `listr2` into one coordinated bump (`rangeStrategy: pin`), mirroring the `pnpm.overrides` pin each app repo carries. This repo is the designated home for cross-repo shared config generally (this preset, `platform-versions.json`); a short-lived separate `mfe-pot-renovate` repo and the `mfe-pot` meta repo were both considered and rejected for that role.
- BFF request/response contracts stay lightweight (hand-written TS interfaces in each `libs/<domain>/data-access`, not generated from a schema) — a deliberate, acceptable scope limit for this PoT, not an oversight.

**A real gotcha discovered building the publish pipeline**: a `libs/shared/*` package's `dist/` folder must never exist *inside that lib's own directory* except transiently during an actual `npm publish`. Once it does (e.g. from manually running `nx build shared-ui-gcds`, which — per its `tsconfig.lib.json` — outputs there so a *published* package's `package.json` "main" field resolves correctly), Nx's jest resolver starts preferring that plain-`tsc`-compiled output over the TS source for any *other* project's test that imports the package. A plain `tsc` build never inlines Angular's `templateUrl`/`styleUrl` the way `jest-preset-angular`'s source transform does, so any Angular component in that lib (today: `MscaAppFrame` in `shared-ui-gcds`) breaks everywhere except the lib's own test suite, with an opaque "component not resolved: templateUrl... did you run resolveComponentResources()?" error. Confirmed by literally deleting the stray `dist/` folder and watching `shell:test` go from consistently failing to consistently passing. Fixed at the tooling level: `tools/scripts/publish-shared-lib.mjs` builds via the normal `nx run shared-<name>:build` target (which outputs to the shared, out-of-the-way `dist/out-tsc/libs/shared/<name>/src/` tree, safe because nothing resolves a package there), copies only that lib's own output slice into `libs/shared/<name>/dist` for the moment `npm publish` needs it, then deletes it again. If `nx test` ever starts failing on an Angular-component shared lib with this exact error, check for a stray `libs/shared/*/dist` folder before assuming the code is wrong.

### Apps are thin, libraries hold the real functionality
`apps/<name>` is a thin federation host (bootstrap, routing table, DI wiring, federation exposes). The real components/business logic live in `libs/<name>/feature-*` and `libs/<name>/ui-*`. This is driven by a concrete requirement: Job Bank's components need to work both federated into this shell *and* on the standalone real-world Job Bank site, which won't share this shell's wiring at all. Every MFE follows this pattern, for consistency, so any feature library could later be re-packaged (npm library, different host, own repo) without a rewrite.

Feature libraries depend only on **injected DI tokens** for cross-cutting concerns (identity, locale, telemetry) — never on this shell's concrete `auth`/`i18n` implementations directly. `apps/<name>` wires in the concrete implementation; a different host would wire in its own.

### Federation
- **Native Federation** (`@angular-architects/native-federation`), not Webpack Module Federation — matches Angular's modern esbuild-based builder. Nx does not have first-class Native Federation support today (its built-in MF tooling is webpack-based), so this is wired per-project using Native Federation's own builder/dev-server, replacing (not extending) Nx's default Angular executors on the federated projects.
- Remote discovery goes through a `RemoteRegistryProvider` abstraction, not a static file read directly — entries carry name, URL, route prefix, and version. Three implementations: Strapi-backed (local dev — edit a "Remote" entry in Strapi and the shell picks it up next load, no rebuild/restart), static baked-JSON (for a hosted/no-CMS deployment), in-memory stub (tests). `apps/shell/src/main.ts` itself inlines the Strapi-first-with-fallback logic rather than using this abstraction directly (see the bare-specifier gotcha), falling back to `runtimeConfig.remotes` instead of a static JSON provider once Kubernetes hosting lands (see "Hosting: Kubernetes + Helm" below). On a version mismatch, the shell warns and loads anyway — this is a demo tool, not a production compatibility gate.
- Two federation patterns are proven: (a) each MFE exposes a routed module the shell lazy-loads, and (b) `dashboard` exposes one standalone widget (payment-history) that `employment-life-events` renders inline. Scoped to one widget deliberately.
- **Cross-remote widget composition is host-mediated, not remote-to-remote.** A remote calling `loadRemoteModule` on *another* remote is tempting but doesn't work: `@angular-architects/native-federation`'s `loadRemoteModule` awaits an in-memory promise that only the calling bundle's own `initFederation()` resolves. Since we deliberately don't share the `@angular-architects/native-federation`/`@softarc/native-federation` packages themselves (see federation.config.mjs comments — sharing them breaks the *host's* own bootstrap import, a chicken-and-egg failure), every remote bundles its own disconnected copy of that runtime, so a nested `loadRemoteModule` call from within a remote just hangs forever with no error. The fix: the **shell** (which always has a working federation runtime) loads the cross-remote widget itself and hands the resolved component class down to the consuming remote via an injected DI token — see `PAYMENT_HISTORY_WIDGET_LOADER` in `employment-life-events-feature-guided-journey` and where the shell provides it in `apps/shell/src/app/app.routes.ts`. This is also just a specific case of the existing "feature libraries depend on injected DI tokens for cross-cutting concerns" principle above, not a special exception.
- **Dev-server caching gotcha**: the Angular/Vite dev-server's persistent cache (`.angular/cache/<version>/<project>/`) can serve a stale compiled version of a `libs/` file that a *different* app project depends on via a TS path-mapped bare import (not a relative path) — edits to the lib don't reliably trigger a recompile of the consuming app's cached output. If a change to a shared lib doesn't seem to take effect while a dev server is running, delete that project's `.angular/cache` entry and restart before assuming the code is wrong.
- Each remote exports its own `REMOTE_PROVIDERS` (HTTP client, interceptors, its Transloco scope), applied at its own bootstrap and on the routes/component the shell mounts — a lazy-loaded remote does not inherit the host's provider tree for free.
- `federation-runtime` wraps every dynamic remote import in explicit failure handling — a failed remote/widget degrades just that route/widget, not the whole shell.
- **A plain Nx library must never import `@angular-architects/native-federation` directly** — it can silently get its own bundled copy of the package, separate from the one `main.ts` initializes. Native federation's builder only keeps the package external (pointing at the one shared dev-optimized/prod-shared copy) for the entry points and exposed modules it explicitly manages; an ordinary library chunk that transitively imports it (e.g. one split out by the bundler for its own reasons) falls back to esbuild's default "bundle everything not marked external" behavior, inlining a second copy with its own disconnected module-scoped state. Symptom: `loadRemoteModule` calls made through that copy hang forever — no error, no rejection, because that copy's internal `federationPromise` is only ever resolved by *its own* `initFederation()` call, which never happens. (Confirmed by comparing served bundles: `main.js`/the bootstrap chunk correctly referenced the shared `@fs/.../vite/deps/@angular-architects_native-federation.js` URL; a separately-chunked library instead had the package's entire source inlined with a fresh, never-resolved `federationPromise`.) Fix: the library takes `loadRemoteModule` via an injected `RemoteModuleLoader` (see `REMOTE_MODULE_LOADER` in `shared-federation-runtime`) instead of importing the package itself; only `apps/<name>`'s own code provides the real function, sourced from the same import `main.ts` uses. This is the same pattern as `PAYMENT_HISTORY_WIDGET_LOADER` and exists for the identical reason.

### Federation-sharing policy
Default to **not** marking a library as a federation "shared" singleton. Every shared entry re-couples the apps' deploy/version schedules — the opposite of the independence goal — so it's only worth it for dependencies that are large, stable, and low-churn enough that the coupling cost is clearly repaid. Today that bar is met by **Angular core + RxJS**, plus **`@gcds-core/components` and `@gcds-core/components-angular`** (see GCDS section below for why), and nothing else. It is explicitly *not* met by feature/business-logic libraries or anything with active churn — which is why the mock auth session and active locale cross remote boundaries as a small versioned DTO + broadcast event instead of a shared singleton. Weigh any future sharing candidate against this same bar.

### GC Design System (GCDS)
`libs/shared/ui-gcds` wraps `@gcds-core/components-angular` (the current package — `@cdssnc/gcds-components*` are deprecated). `MscaAppFrame` is the shared header/footer app frame; **only the shell uses it** — remotes render content only, never their own header/footer.

- **GCDS must be a federation-shared singleton**, unlike most libraries under the sharing policy above. The underlying custom elements are already safely idempotent on their own (GCDS checks `customElements.get()` before calling `define()`), but the **Angular wrapper classes** (`GcdsHeader`, `GcdsSignature`, etc.) are separate per-bundle classes — without sharing, two federated bundles both defining their own copy on the same page trips Angular's `NG0912` "component ID generation collision" warning. Confirmed fixed by adding both packages to every app's `share()` config.
- **`gcds-header` has no default/unnamed slot** — only named ones (`signature`, `menu`, `banner`, `breadcrumb`, `search`, `toggle`, `account`, `skip-to-nav`). Content without an explicit `slot="..."` attribute is silently dropped by the browser, not an error — if a GCDS component's projected content isn't appearing, check the slot name against the component's source (`node_modules/@gcds-core/components/dist/collection/components/<name>/<name>.js` has `@slot` JSDoc comments) before assuming it's a bug elsewhere. `gcds-top-nav`'s content, by contrast, needs actual `gcds-nav-link`/`gcds-nav-group` children (its internal CSS doesn't style a plain `<ul><li><a>`).
- Angular template bindings on GCDS components use the **camelCase property name** (`[skipToHref]`, `[contextualHeading]`), not the kebab-case HTML attribute — these are real `@Input()`-backed Angular components (detached-CD, form-control-aware), not raw custom elements needing `CUSTOM_ELEMENTS_SCHEMA`.

### Security: defense in depth
The shell performs a stubbed mock Sign-In-Canada/GCKey login (`apps/shell/src/app/login-page`, no real IdP) via `createMockSession()`. The resulting session crosses remote boundaries the same way active locale does — `sessionStorage` + a `window` `CustomEvent` broadcast (`libs/shared/auth/src/lib/session-sync.ts`), not a shared federation singleton — because it's exactly the same kind of small, versioned, per-session state the sharing policy above already covers. **Each app enforces its own security** — never assume "the shell let me navigate here, so I'm authorized." The shell has real sub-routes, so it uses a normal Angular router guard (`requireSessionGuard`) on `/dashboard` etc., redirecting to `/` when there's no session. Remotes have no internal routing in this PoT (each exposes one component), so each one's own `App` component checks its own claim directly (`hasClaim(getStoredSession(), CLAIM_X)`) and renders a "sign in required" state instead of its content when absent — same principle as a route guard, different mechanism, since there's no sub-route to guard. Verified concretely: a remote hit directly at its own dev-server origin, with no shell and no session, independently blocks its own content — it doesn't rely on the shell having stopped it. `libs/shared/auth` (session model, `session-sync`, `createMockSession`, claim constants, `requireSessionGuard`) is bundled normally by each app, not a federation singleton, since it's stateless logic.

### Independent testability
Every app must be buildable, serveable, and testable entirely on its own, using stub implementations of whatever it's normally handed (auth token, locale, registry entries) — without the shell or any sibling remote running. The composed `mfe-e2e` Playwright suite proves the apps work together; each app's own standalone test target proves it hasn't grown a hidden runtime dependency on the shell. Treat a regression here as a real regression, not an acceptable cost.

`apps/mfe-e2e` is a plain hand-written Nx project (`@nx/playwright:configuration`'s generator only *adds* Playwright to an existing project, so this one — a standalone composed suite with no single "host" app — was created by hand instead) covering routed federation across all 4 remotes, cross-remote widget embedding, the language-switch broadcast, the BFF-backed golden path (apply for a job, apply for EI, confirm it lands in the dashboard overview), and `@axe-core/playwright` WCAG 2.2 AA scans on every route (currently zero violations). `playwright.config.ts`'s `webServer` array starts all 9 local processes (5 frontends + 4 BFFs) so the suite is self-contained in CI, with `reuseExistingServer` so local iteration can attach to an already-running stack instead of restarting everything. Three non-obvious things had to be right for this to work:
- **`webServer.command` runs from the config file's own directory, not the workspace root** — `nx run <project>:serve` needs to resolve workspace-relative paths (`tsconfig.base.json` etc.), so every entry sets `cwd` to the actual repo root explicitly.
- **Starting many `nx run` processes concurrently contends for the single shared Nx daemon hard enough to crash it** (SQLite task-history writes racing) — each spawned process sets `NX_DAEMON=false` so it runs standalone instead of coordinating through that daemon.
- **Every BFF has a plain, stateless `GET /health`** used for Playwright's readiness check specifically because the natural-looking alternative — probing a real domain endpoint like `/api/claims?applicantSub=...` — depends on mutable in-memory state (a claim that may or may not exist yet) and intermittently reported "not ready" depending on what earlier test/demo runs had left behind.

**Known gap**: the 4 BFFs hold in-memory state with no reset endpoint yet, so repeated local/CI runs accumulate applications and claims rather than starting from zero — the golden-path e2e test deliberately uses loose assertions (`.first()`, existence checks) rather than exact counts for this reason. A `pnpm demo:reset` command (already called for in the demo narrative below) would fix this the same way it fixes repeatable live demos.

### Minimize cross-MFE shared state
Independence is the point of this architecture. Shared runtime state is a liability to justify, not a default. Today it's limited to: the Angular/RxJS singleton, the auth token DTO, and the active locale. Any proposal to share more goes through the sharing-policy bar above.

### Backends: BFF pattern, where it earns its keep
`job-bank` and `employment-insurance` each have their own dedicated backend (`job-bank-bff` on :3001, `employment-insurance-bff` on :3002) — realistic shape, and it pays off the "Job Bank must be reusable outside this shell" requirement (a standalone consumer needs a real API, not client-side mock state). "Tell us once" data (profile, address, payments, correspondence) is served by its own `client-profile-service` (:3003) rather than a shared in-memory lib — an in-memory lib would silently give each independently-built remote its own disconnected copy of "the profile," breaking the exact behavior it's meant to demonstrate. `dashboard-bff` (:3004) composes MSCA-D's cross-benefit overview by calling the other three services over real HTTP — not by importing another domain's in-memory state — which is what actually makes the independence claim true.

All four are plain Express/TypeScript apps (`@nx/node:application`, `framework=express`), each with an `export function createApp(): Express` (in `app.ts`) separate from `main.ts`'s `.listen()` call, so tests exercise the real Express app via `supertest` without a live socket. **Their inferred lint target is named `eslint:lint`, not `lint`** — the `@nx/node` generator doesn't add an explicit `lint` target the way the Angular apps/libs do (those override it manually); run `nx run <bff>:eslint:lint` directly, or note that a plain `nx run-many --target=lint` silently skips these four projects rather than failing.

`dashboard-bff`'s fan-out (`overview.ts`) has an explicit partial-failure contract, `fetchJson()`'s `UpstreamResult<T>` (`{status:'ok', data} | {status:'unavailable'}`): a slow/failed/non-2xx upstream degrades only its own tile, never the whole response. A citizen with no EI claim on file gets a 404 from `employment-insurance-bff` — that's handled as a distinct case (`{status:'ok', data: null}`), not `unavailable`, since "no claim yet" is a legitimate state, not a service failure. Verified live by killing `client-profile-service` (payments tile alone degrades, active-applications tile — sourced from the other two services — keeps rendering real data) and separately killing `job-bank-bff` (the inverse: active-applications degrades, payments keeps working).

Each frontend talks to its backend through a thin `<Domain>ApiClient` interface + `Http<Domain>ApiClient` implementation, in a dedicated `libs/<domain>/data-access` library (mirrors the `ContentClient`/`RemoteRegistryProvider` pattern) — an `InjectionToken` per client, provided in that app's own `remote-providers.ts` from its own `runtime-config.ts` (see "Hosting: Kubernetes + Helm" below — this replaced `environment.ts` base URLs). Feature libraries inject the token, never the concrete class, for the same reason they take locale/identity via DI (see "Apps are thin" above).

**The cross-remote payment-history widget needed the same component+providers pairing as `RemoteRouteHost`, for the identical reason.** Once the widget started injecting `PAYMENT_HISTORY_API_CLIENT`, embedding it in `employment-life-events` via the existing `PAYMENT_HISTORY_WIDGET_LOADER` broke: the widget was mounted via `createComponent()` with no explicit `environmentInjector`, so it ran in `employment-life-events`'s own injector, which has no idea what the widget needs. Fixed by changing `PaymentHistoryWidgetLoader`'s return type from `Promise<Type<unknown>>` to `Promise<{ component, providers }>` — the shell now also loads dashboard's `./RemoteProviders` alongside `./PaymentHistoryWidget`, and `employment-life-events` applies those providers via `createEnvironmentInjector` before calling `createComponent`, exactly like `RemoteRouteHost` does for routed remotes.

`dashboard`/MSCA-D and `employment-life-events` don't get their own dedicated backends — there's no distinct bounded context there that justifies one. Not every MFE needs a BFF; add one only where it earns its keep.

### i18n
UI chrome text uses **Transloco** (runtime-switchable, per-MFE translation loading — required since remotes are independently deployed and can't share Angular's compile-time i18n). Each app calls `provideMfeTransloco(assetBaseUrl)` (`libs/shared/i18n`) with its own computed asset base URL. Active locale crosses the federation boundary as a `localStorage` value + `window` `CustomEvent` broadcast (`locale-sync.ts`) — deliberately not a federation singleton, per the sharing policy above. Page content is bilingual and CMS-driven through the `ContentClient` abstraction (`libs/shared/content-client`): `StrapiContentClient` locally (real EN/FR entries seeded into the local CMS), `StaticContentClient` as a no-CMS fallback and for tests, same interface either way. `dashboard`'s overview text was the original reference example (`apps/dashboard/src/app/app.ts`); the same `content-client.token.ts`/`createContentClient` pattern was later repeated for `job-bank`, `employment-insurance`, and `employment-life-events` too, each rendering one CMS-driven intro block (`<app>.intro` key) at its own app-shell level, above its feature libraries. All four are seeded in `tools/cms/strapi/src/index.ts`'s `PAGE_CONTENT` array.

**A remote mounted via `RemoteRouteHost`'s child `EnvironmentInjector` needs its OWN Transloco instance, and two Angular DI defaults fight that:**
- `TranslocoService` is declared `providedIn: 'root'` by the library, and `provideTransloco()` never re-provides the service class itself — only its config/loader tokens. Without an explicit override, *every* remote resolves the same singleton (whichever app constructed it first, i.e. the shell's), silently using the shell's loader/config/asset base URL instead of its own — symptom was `Missing translation for '<key>'` console warnings on remotes whose keys aren't in the shell's translation files, plus i18n asset fetches all hitting the shell's origin regardless of which remote rendered. Fix: `provideMfeTransloco()` explicitly re-provides `TranslocoService` (a bare class provider) alongside the config/loader, forcing a fresh instance per environment injector.
- `provideAppInitializer()` (`APP_INITIALIZER` under the hood) only runs for the injector `bootstrapApplication` creates at the true app root — it never fires for an injector created later via `createEnvironmentInjector`, which is exactly how `RemoteRouteHost` mounts a remote's providers. A remote's locale-sync subscription (the thing that makes it actually react to the cross-remote language-switch broadcast) would silently never run. Fix: use the `ENVIRONMENT_INITIALIZER` multi-provider token instead, which Angular runs for *any* environment injector, root or child.

Verified end to end: switching language via the shell's toggle updates the shell's own nav chrome *and* an independently-loaded remote's chrome simultaneously, each fetching its own `en.json`/`fr.json` from its own origin off the single broadcast event.

**Known gap**: `dashboard`'s payment-history widget (embedded live in `employment-life-events`) still renders static English mock data — heading, benefit names, dates, currency formatting — none of it wired to Transloco/locale-aware formatting yet. It's mounted via the consuming remote's own environment injector (no explicit `environmentInjector` override on its `createComponent` call), so whichever host embeds it would need to supply the translation key itself, or the widget needs its own scope. Left as-is for now — full data/currency/date bilingual fidelity is a later demo-narrative beat (see "the bilingual switch is demoed as a real flex" in the plan), not part of the basic chrome-i18n proof.

### Local CMS / federation directory: Strapi
`tools/cms/strapi` is a real Strapi 5 (TypeScript, SQLite) project, run locally via its own Helm chart (`charts/strapi`) deployed to the local `kind` cluster with `pnpm deploy:local` (`tools/deploy-local.sh`) — see "Hosting: Kubernetes + Helm" below for the general build/kind-load/helm-upgrade loop this follows. Two content types, defined as code (not created by hand in the admin UI) under `tools/cms/strapi/src/api/`:
- **`page-content`** — bilingual (Strapi i18n plugin, `en`/`fr` locales) page content, read via `ContentClient`.
- **`remote`** — the federation directory (name, url, routePrefix, version), read via `RemoteRegistryProvider` (`libs/shared/remote-registry`). Editing an entry in the Strapi admin and reloading the shell picks up the change with no rebuild — this is the actual "live directory server" capability, not just a config file.

Seeding is a **bootstrap script** (`tools/cms/strapi/src/index.ts`), not a `strapi export` archive — it's idempotent (checks before creating) and also grants the Public role read access to both content types and creates the `fr` locale, so `pnpm deploy:local` produces a complete, working environment on every fresh pod with zero manual admin-panel steps. Local-dev-only dummy secrets (`APP_KEYS` etc.) are committed directly in `charts/strapi/values.yaml` for the same reason — never reuse them for anything real.

Each seeded `remote.url` is read from a `REMOTE_<NAME>_URL` env var, falling back to the `nx serve` localhost dev port (`http://localhost:4201/remoteEntry.json` etc.) if unset — **not** hardcoded, despite looking like static seed data. This matters once Strapi is actually deployed (see `charts/strapi` below): a *reachable-but-wrong* directory is worse than an unreachable one, since `resolveFederationManifest()`/`ContentClient` in each app only fall back to their own configured default when Strapi itself is unavailable, not when its data is stale.

The shell reads the registry via `RemoteRegistryProvider` in `apps/shell/src/main.ts` (inlined logic, not the shared lib — see the bare-specifier gotcha above), with a 3s timeout and fallback to `runtimeConfig.remotes` if Strapi is slow/unreachable — see "Hosting: Kubernetes + Helm" below for what populates that value (dev defaults locally, a container-injected map once deployed). This replaced the old baked `federation.manifest.json` file entirely.

**`charts/strapi`** deploys this as its own Helm release, live-validated on the local `kind` cluster alongside all 5 apps (see "Hosting: Kubernetes + Helm" below for the general pattern this deliberately doesn't reuse). Exposed at Ingress host `cms.mfe-pot.local` — "cms", not "strapi", since the latter is an implementation detail no citizen-facing or demo-facing hostname should say. `charts/strapi/values.yaml` sets each `REMOTE_<NAME>_URL` to the real sibling app's Ingress hostname, and `mfe-pot-shell`/`mfe-pot-dashboard`'s own chart `values.yaml` `strapiBaseUrl` fields point at the same `http://cms.mfe-pot.local` — confirmed end to end by curling both apps' live `env.js` plus Strapi's `/api/remotes`/`/api/page-contents` through the Ingress. `tools/deploy-local.sh` (`pnpm deploy:local`) is the one-command build/kind-load/helm-upgrade loop for it, matching each app repo's own `deploy:local` script.

### Hosting: Kubernetes + Helm (pattern proven for all 5 apps, CI/AKS still open)
Firebase Hosting has been retired (`firebase.json`, `.firebaserc`, and the `build-hosted` copy-step target are gone) in favor of **Kubernetes — AKS in the cloud, `kind` locally — deployed via Helm**. Neither AKS nor an Azure Container Registry exist yet; the plan is to get the whole pattern working and validated against `kind` first, then provision Azure and add a Stage 2 CI step once that's proven. The pattern was proven first for job-bank, then repeated for employment-insurance, dashboard, shell, and employment-life-events — **every app repo now has its own Dockerfile(s) and Helm chart, each validated live on a local `kind` cluster** (see "Monorepo → per-app repos" above for the gotchas hit along the way). What's still open is per-repo CI (no repo has the kind-based validation stage wired into GitHub Actions yet) and everything Azure-side (AKS/ACR provisioning, Stage 2 CI, the two library charts pushed to a registry as OCI artifacts — they're still referenced by local `file://` sibling-checkout paths).

**Runtime config, not build-time — done.** One container image per app gets built once and promoted across environments unchanged; environment-specific values (BFF URLs, Strapi URL, the remotes map) come from a Helm-chart-supplied ConfigMap injected at pod startup instead of Angular's old `fileReplacements`/`environment.prod.ts` swap:
- **`@tn4consulting/shared-runtime-config`** (`libs/shared/runtime-config`) exports `getRuntimeConfig<T>(devDefaults: T): T`, which merges `window.__mfePotEnv` over dev-time defaults. Each app has its own `src/runtime-config.ts` calling this with just the fields it needs (e.g. `apps/dashboard/src/runtime-config.ts` has `strapiBaseUrl`, `dashboardBffBaseUrl`) and imports `runtimeConfig` wherever it previously imported `environment` (`remote-providers.ts`, `app.ts`). The old `environments/` directories and `fileReplacements` build-config blocks are deleted everywhere they existed. Note: `client-profile-service` is BFF-only, never reachable directly from the browser, so dashboard's `runtimeConfig` deliberately has no `clientProfileServiceBaseUrl` entry — `HttpPaymentHistoryApiClient` goes through `dashboard-bff`'s own `/api/payments` proxy instead.
- **`apps/shell/src/main.ts` can't use the shared package** — same bare-specifier-from-`main.ts` constraint as `shared-remote-registry` (see the gotcha above) — so it inlines its own small `{ ...devDefaults, ...window.__mfePotEnv }` merge instead. Its config shape is `{ strapiBaseUrl, remotes }`, where `remotes` (a `Record<name, remoteEntryUrl>`) is what the old baked `federation.manifest.json`/`.prod.json` swap-file pair used to hold. `resolveFederationManifest()` still tries Strapi first with the existing 3s timeout, falling back to `runtimeConfig.remotes` instead of the old bundled JSON file.
- **`window.__mfePotEnv` needs an actual place to be set before the app boots**: every frontend that reads runtime config (`shell`, `dashboard`, `job-bank`, `employment-insurance`) has a `public/env.js` (`window.__mfePotEnv = {};` — a harmless no-op default for `nx serve` and for the image's baked-in placeholder) loaded via a plain blocking `<script src="env.js"></script>` in `index.html`'s `<head>`, placed before Angular's deferred module-script tags so it always runs first regardless of build output ordering. In a container, `tools/docker/frontend-entrypoint.sh` overwrites this exact file at startup with the real values.
- Verified end to end: full `nx run-many -t lint,test,build --all` green across all 27 projects, plus a live smoke test (`nx serve shell` + `nx serve dashboard`) confirming the dev-default fallback path behaves identically to the old `environment.ts` values.

**Docker images, Helm library charts, and kind validation — proven for job-bank first, then repeated for the other 4.**
- **Frontend image** (`Dockerfile` in each app repo's `apps/<app>/`, same shape for every frontend): multi-stage — builder stage runs `pnpm install` + `nx build <app> --configuration=production`, runtime stage is plain `nginx:alpine` serving `dist/apps/<app>/browser`. `tools/docker/nginx.conf` (same file, copied into each app repo) sets the same CORS/no-cache/immutable-cache headers the old `firebase.json` did per app. `tools/docker/frontend-entrypoint.sh` is dropped into nginx's `/docker-entrypoint.d/` (the official image auto-runs every script there before starting nginx, so no custom `ENTRYPOINT` override is needed) and writes whatever `MFE_POT_ENV_JSON` env var it finds into `env.js`, defaulting to `{}` if unset. Shell and employment-life-events have no BFF, so their repos have only this one Dockerfile.
- **BFF image** (`Dockerfile` in each owning app repo's `apps/<bff>/` — `job-bank-bff`, `employment-insurance-bff`, `dashboard-bff`): multi-stage — builder stage `nx build <bff>`, runtime stage plain `node:22-alpine` copying `dist/apps/<bff>` and the **full workspace `node_modules`**, not a pruned subset, since each extracted repo is now its own single-package workspace with a real top-level `package.json` — the pruning problem this used to have (no per-project `package.json` to scope from) resolved itself once extraction happened, per the plan. **A real gotcha caught here**: the BFF's `main.ts` binds `process.env.HOST ?? 'localhost'` (fine for local dev), but inside a container `localhost` is the container's own loopback interface — a Pod's Service can never reach a process only listening there despite it looking healthy from inside its own container. Every BFF image sets `ENV HOST=0.0.0.0` to fix this; this is an image/chart-level fix, not a code change, since `HOST` is already an env var the app already reads.
- **Helm library charts** (`charts/mfe-frontend-lib`, `charts/mfe-backend-lib`, live in this repo permanently) hold reusable Deployment/Service/ConfigMap named-templates (`type: library` in `Chart.yaml`, never installed directly) — `mfe-frontend-lib.deployment`/`.service`/`.configmap` and the `mfe-backend-lib` equivalents. Each has a `README.md` documenting its values contract. **Ingress is deliberately not part of either library chart** — the original design sketch put it there, but a single Ingress needs both the frontend's and backend's Service names together to express the path-based split below, which doesn't fit a per-component library template cleanly; each application chart hand-writes its own single `templates/ingress.yaml` instead.
- **Each app's application chart** now lives in that app's own repo (`charts/<app>` — job-bank's was the template the other 4 followed): `Chart.yaml` declares `dependencies` on both library charts via local `file://../../../mfe-pot-platform/charts/...` sibling-checkout-relative paths (becomes a packaged/OCI reference once the library charts are pushed to a registry), `values.yaml` holds real defaults, `values-kind.yaml` overrides `image.pullPolicy: Never` and `image.tag: kind` for locally-built images with no registry round-trip, and `templates/` is just one-line `{{ include "mfe-frontend-lib.xxx" . }}` / `{{ include "mfe-backend-lib.xxx" . }}` files plus a hand-written `ingress.yaml`. Shell and employment-life-events' charts only depend on `mfe-frontend-lib` (no BFF); `client-profile-service`, staying in this repo, will only depend on `mfe-backend-lib` when it gets a chart.
- **BFFs are exposed under their own frontend's hostname via an Ingress path rule**, confirmed working exactly as designed for every BFF: each BFF's own Express routes already carry the `/api` prefix internally (`/api/jobs`, `/api/claims`, etc.), so the Ingress path rule is a plain prefix match with no rewrite needed, and each frontend's `runtime-config.ts` dev default becomes e.g. `jobBankBffBaseUrl: "/api"` in the chart's `values.yaml` — a same-origin relative path, not a second hostname. `dashboard-bff` is the one exception worth knowing: it calls the other BFFs and `client-profile-service` over real cross-Helm-release **in-cluster Kubernetes Service DNS** (`<service>.default.svc.cluster.local`), not through Ingress, since that traffic is server-to-server, not browser-to-server.
- **Validated live on a local `kind` cluster** for every app (`tools/k8s/kind-config.yaml`, port-mapping 80/443 to the host and labelling the node `ingress-ready=true` per kind's own Ingress guide): `kind create cluster` (note: this environment's Docker daemon reports `Cgroup Version: 1`, and kind's current default node image, built for k8s 1.36, failed `kubeadm init` against it outright — pin an older node image, e.g. `kindest/node:v1.27.3`, which starts cleanly on a cgroup-v1 host) → install the kind-flavoured `ingress-nginx` static manifest → `docker build` each app's image(s) → `kind load docker-image` (no registry needed) → `helm install <app> ./charts/<app> -f values.yaml -f values-kind.yaml` → pods reach Ready → `curl -H "Host: <app>.mfe-pot.local" http://localhost/` returns the real `index.html` (200, `env.js` script tag present) and `/env.js` returns the real ConfigMap-injected values, not the image's `{}` placeholder. dashboard's validation was the strongest proof of the cross-service design specifically: with job-bank and employment-insurance already deployed in the same cluster, `dashboard-bff`'s `/api/overview` returned real `"ok"` data for the tiles sourced from those two services while correctly degrading to `"unavailable"` for the `client-profile-service`-sourced tile (not deployed) — the partial-failure contract working across real Helm releases, not just in a single process.

**The kind-based CI validation stage is now wired into all 5 app repos'** `.github/workflows/ci.yml`: lint/test/build, then build the image(s), spin up an ephemeral `kind` cluster (checking out this repo as a sibling directory for the library charts' `file://` dependency and `tools/k8s/kind-config.yaml` — a public-repo checkout, no extra secret needed), `helm install` that app's own chart, and curl the Ingress-routed hostname to confirm it serves. Each workflow deploys only its own app-pair, not the full 5-app topology, so cross-service smoke checks (`dashboard-bff`'s fan-out) deliberately assert reachability rather than depend on sibling BFFs being deployed in the same job.

**Not yet built**: Phase 2 — rewiring `apps/mfe-e2e`'s `playwright.config.ts` `webServer` array, which today only starts `client-profile-service`, to also point at each sibling app repo's checkout so the composed suite covers all 5 apps again (this is the one place a *real* multi-app deployment, not just each repo's own CI, would actually exercise cross-app behavior); pushing the two library charts to a registry as OCI artifacts (still referenced by local `file://` path); AKS/ACR provisioning and the Stage 2 CI step (pushing images to ACR, `helm upgrade --install` against real AKS on push to `main`); a kind-based CI validation stage for this repo generally (unlike the 5 app repos, this repo has no `.github/workflows` for `charts/strapi` yet — validated manually so far, see above). Full design and status in `docs/plans/20260801-1935-mfe-pot-polyrepo-split-and-k8s-hosting.md`.

### Source control & CI/CD
GitHub at `git@github.com:tn4consulting/mfe-pot.git`, GitHub Actions for CI/CD. A single workflow runs `nx affected` for lint/test/build and computes an affected-apps deploy matrix — not hand-maintained per-app path filters, which drift out of sync with real dependencies.

## Design/UX fidelity

Within what GC design/accessibility standards permit, look/feel/behavior should take visible inspiration from the real **jobbank.gc.ca** (fully public, no login required — a direct reference for `job-bank`) and the **public-facing "My Service Canada Account" pages on canada.ca** (landing/login pages — a reference for `shell` branding and nav chrome). MSCA's authenticated dashboard is **not** publicly browsable without a GCKey/Sign-In Partner login, so the interior screens (`dashboard`, `employment-insurance`, `employment-life-events`) are our own extrapolation using GCDS patterns and general knowledge of comparable GC account portals — not a verified reproduction. Say so explicitly in the docs rather than leaving it implicit.

## Linting

Lint with Angular-aware TypeScript rules — `typescript-eslint` + `angular-eslint`, not just generic TypeScript lint — across all Angular apps/libs. **Follow lint rules; don't suppress them to get past a check.** A failing rule means fix the code, or, if the rule is genuinely wrong for a case, change the rule deliberately and say why — not an inline disable comment and move on.
