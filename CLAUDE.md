# mfe-pot-platform — Government of Canada MFE Proof of Technology

## What this is

A proof-of-technology (PoT) demonstrating React micro-frontend (MFE) architecture, following Government of Canada design/accessibility/bilingual standards. It is framed around a fictional ESDC "you lost your job" scenario — a citizen-facing shell branded as a mock of **"My Service Canada Account" (MSCA)** aggregating four independently-built MFEs — but **this is fictional scaffolding to give the architecture real shape, not a production build**. GC design, accessibility, and bilingual standards are followed faithfully because proving those out *is* the point of the exercise. Citizen data is intentionally mocked/simplified (no real PII, no compliance/security hardening in scope); authentication is a real authorization-code + PKCE flow against a mock IdP (`mock-idp`, `libs/shared/auth-server`) that issues genuinely signed/verified JWTs — see "Security: defense in depth" below — just not a connection to a real government IdP.

**The family completed its Angular-to-React migration in August 2026** — all 5 frontends were originally Angular, converted one at a time (smallest first) to React, with Angular removed entirely rather than kept as a fallback. Full history and rationale lives in the `mfe-pot` meta repo's `docs/plans/` (see "Planning documents" below); this file describes the architecture as it exists today, post-migration.

**This repo is the platform repo of a 6-repo split** — it started as a single Nx monorepo containing all 5 frontends and has since been carved into 6 independent repos (the split is done; see "Monorepo → per-app repos" below for how and "Not yet built" for what's left in the surrounding hosting/CI work). This repo now holds only what's genuinely shared or has no single frontend owner: `libs/shared/*` (published as `@tn4consulting/shared-*` packages), the composed `mfe-e2e` suite, Strapi, and the two Helm library charts. The 5 frontends (plus their own dedicated BFFs) live in their own sibling repos. **This file remains the durable architecture reference for the whole family** — the sibling repos' own `CLAUDE.md` files point back here for rationale rather than duplicating it, so keep this file accurate for the family as a whole, not just this repo's own directory contents; where a section describes code that now lives in a sibling repo, that's noted inline. See `../CLAUDE.md` (the `mfe-pot` meta repo one level up) for the full repo map and cross-repo mechanics.

Full design rationale lives in the `mfe-pot` meta repo's **`../docs/plans/`** (project-wide planning docs live one level up, not in this repo — see "Planning documents" below for why): see `mfe-pot-initial-design.md` for the initial design, kept updated with an "Updates Since Initial Approval" section as decisions evolve, and `20260801-1935-mfe-pot-polyrepo-split-and-k8s-hosting.md` for the full history of the split itself. This file is the durable, living summary — update it when architecture decisions change; don't let it drift from what the code actually does.

## Tooling

Runtime versions are managed with **asdf** (`.tool-versions` at repo root pins `nodejs`). If you hit a `require() of ES Module ... not supported` error from a toolchain package, check the Node version first — several build-time dependencies (e.g. `magic-string`) ship ESM-only builds that need Node's unflagged `require(esm)` support (Node ≥ 22.12), not just any Node 22.x. Package manager is **pnpm** (not asdf-managed; installed globally/via corepack). Local CMS/registry infra (Strapi) runs on the local `kind` cluster via its own Helm chart (`charts/strapi`, deployed with `pnpm deploy:local`) — needs Docker (for `kind`) running; see "Local CMS / federation directory: Strapi" below.

**Angular-era gotchas (zoneless testing, `fileReplacements`, ng-packagr `dist/` pollution, and others) have been moved out of this living reference** now that no app in the family runs Angular — they're real, hard-won lessons but no longer active concerns for anyone working in this codebase today. Full detail lives in the migration history doc under the `mfe-pot` meta repo's `docs/plans/` (see "Planning documents" below) if you're ever debugging something that smells like a leftover from the Angular era.

**esbuild specially recognizes `new URL('...', import.meta.url)` and rewrites it for asset bundling** — even in dev mode, and even when the intent is just "compute my own serving origin" (needed so a federated remote's i18n/asset requests resolve against its own origin, not the shell's). The rewrite hijacks the computation, producing a bogus dev-server-relative disk path instead of the real serving URL. Fix: split it across two statements — `const moduleUrl = import.meta.url; const assetBaseUrl = new URL('.', moduleUrl).href;` — the special-casing only triggers on the exact inline single-expression pattern. See any remote's `asset-base-url.ts`.

**Bare-specifier workspace libraries can't be imported from an app's own entry (`main.tsx`).** Same root cause as the native-federation-sharing chicken-and-egg problem: `main.tsx` runs before Native Federation's import-map/shared scope exists, and under `shimMode` *any* bare (non-relative) specifier resolves through that import map — including plain internal libraries that were never marked `shared`. It works fine everywhere else (anything reached via a federated `./Component` expose, e.g. `App.tsx` importing `shared-content-client`), just not in `main.tsx` itself. `apps/shell/src/main.tsx` inlines the small amount of fetch logic it needs rather than importing `shared-remote-registry`, for exactly this reason.

## The apps

The 5 original frontends now live in their own repos, each with its own `CLAUDE.md` pointing back here for shared rationale — plus a second, minimal host app proving the federation pattern generalizes to more than one host:

- **`mfe-pot-msca-shell`** — host app, branded MSCA: app frame, GC header/footer, language switcher, PKCE-based mock Sign-In-Canada-style login (against `apps/mock-idp` — see "Security: defense in depth" below), runtime federation manifest reader. Composes all 4 remotes. No BFF of its own.
- **`mfe-pot-job-bank-shell`** — second, minimal proof-of-concept host — composes only the job-bank-mfe remote's own `./Component`, no sidebar nav (one destination), distinct PKCE client. No BFF of its own.
- **`mfe-pot-dashboard-mfe`**, branded **MSCA-D** — 360° cross-benefit overview (eligible benefits, active applications, "my tasks"), payment history, correspondence, "tell us once" profile maintenance. Owns `dashboard-bff`.
- **`mfe-pot-job-bank-mfe`** — job search and apply. Owns `job-bank-bff`.
- **`mfe-pot-employment-insurance-mfe`** — EI application, claim status, EI reporting. Owns `employment-insurance-bff`.
- **`mfe-pot-life-events-mfe`** — client-centric "you lost your job" guided journey stitching the other three together. No BFF of its own.

**What actually stays in this repo**: `libs/shared/*` (published as `@tn4consulting/shared-*` packages — auth, auth-server, i18n, locale-sync, ui-scds-core, content-client, remote-registry, federation-runtime, federation-config, runtime-config, session-cache), the composed `apps/mfe-e2e` Playwright suite, `tools/cms/strapi`, `apps/mock-idp` (the mock OIDC-shaped IdP — see "Security: defense in depth" below), and the two Helm library charts (`charts/mfe-frontend-lib`, `charts/mfe-backend-lib`). Everything else described below (federation patterns, SCDS usage, i18n, security, BFF contracts) is the shared architecture every app repo follows — the actual source for most of it now lives in the sibling repos, not here.

## Non-negotiable requirements

- **Bilingual**: English and Canadian French everywhere the citizen sees it — UI chrome and CMS content. Contributor/process documentation (`../docs/` in the meta repo, and any platform-specific docs here) is **English-only** by explicit decision — not a GC citizen-facing surface, so it doesn't carry the bilingual requirement the product UI does.
- **Accessibility**: WCAG 2.2 AA, verified by automated tooling (axe), not just manual review or documentation.
- **SCDS** (`@tn4consulting/shared-ui-scds-core`, a self-contained in-house design system consumed directly as custom elements) for all UI. GCDS (`@gcds-core/components`) has been removed from the family entirely; see "Design System (SCDS)" below.
- **Docs kept current** (English-only — see the bilingual note above). Project-wide planning docs live in the meta repo's `../docs/plans/` — see "Planning documents" below.
- **Unit tests** (Jest) and **integration tests** (Playwright, run locally against local stubs/emulators — MSW, a local Strapi container, local BFFs) are required. No dependency on real external services for tests.
- **React** is the framework, for every frontend in the family.
- **TypeScript everywhere** — the React apps/libs and the BFF/service apps alike.
- Each MFE is **independently buildable, testable, and deployable**, and is **loaded dynamically at runtime** as a federated remote — never compiled into the shell at build time.

## Core architecture decisions

### Monorepo → per-app repos (done)
This repo split into 7: this one is the **platform repo** (`libs/shared/*` published as versioned packages, the composed `mfe-e2e` suite, Strapi, the two Helm library charts) plus 6 per-app repos under `tn4consulting` — `mfe-pot-msca-shell`, `mfe-pot-job-bank-shell` (a second, minimal host app added later to prove the federation pattern generalizes beyond one host), `mfe-pot-dashboard-mfe` (+ `dashboard-bff`), `mfe-pot-job-bank-mfe` (+ `job-bank-bff`), `mfe-pot-employment-insurance-mfe` (+ `employment-insurance-bff`), `mfe-pot-life-events-mfe`. BFFs moved with whichever frontend owns them. A fourth BFF-adjacent service, `client-profile-service`, had no single owner and stayed in the platform repo for a time — it's since been removed entirely; its data now lives directly in `dashboard-bff`'s own local stub data (see `mfe-pot-dashboard-mfe`'s `CLAUDE.md`). Local multi-repo dev is **independent sibling clones tied together with a VSCode multi-root workspace file** (`../mfe-pot.code-workspace`) — deliberately not git submodules, because `git worktree add` doesn't auto-init submodule content and this environment's own subagent worktree isolation would silently see empty app directories.

**Note on GitHub remote names**: the `-mfe` suffix cascade (repo/directory name, Nx project name, federation identity, Docker image, Helm chart/release, Ingress host) now reaches the actual GitHub repository name too — `mfe-pot-dashboard-mfe`'s GitHub remote is `github.com/tn4consulting/mfe-pot-dashboard-mfe` (likewise `mfe-pot-job-bank-mfe`, `mfe-pot-employment-insurance-mfe`, `mfe-pot-life-events-mfe`). All 4 were renamed 2026-08 (previously un-suffixed on GitHub only) specifically because the mismatch broke cross-repo tooling that needs the real GitHub name (`gh workflow run`, `gh repo` commands in `../tools/deploy-eks.sh`) — see `../docs/plans/20260808-1500-mfe-pot-aws-eks-terraform.md`. Clone directly using the same name as the local directory; no translation needed anymore.

Each extraction (job-bank first, then employment-insurance, dashboard, shell, life-events) surfaced its own gotcha — worth knowing before touching any app repo's build/publish setup:
- **Published `@tn4consulting/shared-*` packages are ESM (`dist/index.js` uses `export *`) with no `"type": "module"` in their `package.json`**, so Jest's default CJS `require()` can't parse them once resolved through a real `node_modules` (the platform repo itself never hit this — its bare specifiers resolve straight to workspace TS source via `tsconfig.base.json` paths). Every app repo's `jest.config.cts` that imports one of these packages needs `@tn4consulting` added to `transformIgnorePatterns`'s negative-lookahead, the same fix already used for `@softarc`/`@gcds-core`.
- **`pnpm install` inside a Docker build has no access to the host's `~/.npmrc`**, so it 401s fetching `@tn4consulting/*` from GitHub Packages — fixed with a checked-in `.npmrc` (`@tn4consulting:registry=...` + `${NODE_AUTH_TOKEN}` substitution) plus a BuildKit file-mounted secret (`--mount=type=secret,id=npm_token`, read via `cat /run/secrets/npm_token` — this environment's Docker Desktop doesn't support the newer `env=` mount form). CI passes its own `GITHUB_TOKEN` as the same secret.
- **`nx`'s postinstall script can hang indefinitely inside a Docker build** despite its own internal 30s watchdog `setTimeout` — root cause not fully isolated (something upstream of the script's own logic never gets far enough to hit the watchdog). Fixed by removing `"nx"` from `package.json`'s `pnpm.onlyBuiltDependencies` entirely; `nx`'s CLI doesn't need the postinstall hook to function.
- **TypeScript's implicit `@types` auto-inclusion can silently fail to pick up `@types/node`** when `ts-node` compiles `jest.config.cts` via a `tsconfig.json` that doesn't explicitly set `"types"` (root cause not fully isolated — likely an interaction between TS's auto-inclusion and pnpm's symlinked `node_modules/@types` layout under `moduleResolution: "bundler"`). Fixed defensively in every app repo's `tsconfig.base.json`: `"types": ["node"]`, explicit rather than relied-on-implicitly.
- **A missing `.tool-versions`/`pnpm-workspace.yaml` in a freshly-extracted repo silently falls back to the wrong Node version**, reproducing the exact `"require() of ES Module ... not supported"` error this file documents as a Node<22.12 symptom — a real error message pointing at the wrong root cause. Check both files exist and are correct before chasing an ESM/native-federation theory.
- **`federation.config.mjs`'s `exposes` map needs checking on any app that exposes something beyond its own root component** (`dashboard` via `./PaymentHistoryWidget`, `job-bank` via `./JobApplicationsWidget`, `employment-insurance` via `./EiReportingStatusWidget`) — a stale nested path left over from a refactor fails the build with `FsPath ... does not exist`, since only the app-entry expose path gets touched by the usual extraction/conversion steps.
- **Historical, no longer active**: `publish-shared-lib.mjs` still detects ng-packagr libs (presence of `ng-package.json`) and publishes straight from their self-contained `dist/` output — a real requirement while `shared-ui-gcds`/`shared-ui-scds` (Angular-component libraries needing ng-packagr, not the workspace's default tsc build, to publish real Ivy metadata) existed. Both were deleted once every consumer converted to React (see "GC Design System" below), so this code path currently has nothing to detect — left in place rather than ripped out, since it's harmless dead-code-path and a future Angular-shaped lib (unlikely, but not impossible) would need it again.

`@nx/enforce-module-boundaries`'s dep constraints were tightened from a wide-open `sourceTag: '*' -> onlyDependOnLibsWithTags: ['*']` (which didn't actually restrict anything) to real per-scope rules, specifically *before* extracting any app repo — while a violation is still a one-PR fix, not a cross-repo rewrite. This caught a real one: `apps/shell` had a compile-time import of an `life-events`-scoped lib (`PAYMENT_HISTORY_WIDGET_LOADER`), which can't work once they're separate repos — see "Strong contracts" below for the fix.

**Hosting moved from Firebase to Kubernetes (AKS + local k8s via kind), deployed via Helm; `docker-compose.yml` has been removed**, replaced by `charts/strapi` deployed to the local `kind` cluster (see "Local CMS / federation directory: Strapi" below). The prerequisite runtime-config migration (build-time `environment.ts`/`fileReplacements` → a container-injected `window.__mfePotEnv` read at startup) has landed — see "Hosting: Kubernetes + Helm" below for the full mechanism. Still open: AKS/ACR access from CI — deferred until the whole pattern is validated against a local `kind` cluster first.

### Strong contracts between split repos
Versioned npm packages are the actual mechanism, published from the platform repo to GitHub Packages under the `@tn4consulting` scope (GitHub Packages requires the npm scope to match the owning org):
- **`libs/shared/*` ships as `@tn4consulting/shared-<name>`** (auth, i18n, content-client, remote-registry, federation-runtime, ui-scds-core, and others), each with its own `package.json`, built `.d.ts`, and independent version. A breaking change requires a major bump; a consumer that hasn't updated simply fails to build — that's the enforcement, not a convention someone has to remember.
- **`libs/shared/federation-config`** (plain JS, no build step — see below) holds the Native Federation `shared`/`skip`/`features` block every app's `federation.config.mjs` imports instead of hand-copying. Before this existed, all 5 apps carried an identical, independently-editable copy of the singleton version-pinning config — fine in one repo/one PR, but exactly how federation singleton mismatches happen silently once 5 repos can each drift it independently.
- **`payment-history-widget-loader.token.ts` lives in `shared-federation-runtime`**, not in `life-events`'s own feature library where it used to live — that was the module-boundary violation above. Both the shell repo (which provides the token's value) and the life-events repo (which injects it) now depend on the same published package instead of one repo importing the other's source.
- **`platform-versions.json`** (repo root) is the single checked-in source of truth for the React/SCDS/Node/TypeScript versions every app repo must stay aligned on — required because Native Federation's shared-singleton contract silently breaks at runtime (no compile-time warning across repos) if one app drifts its React or `@tn4consulting/shared-ui-scds-core` version relative to the others. A future version-alignment check can read each deployed remote's live `remoteEntry.json` (which already lists every shared package's exact resolved version) and each BFF's `/health`, and assert they all agree with this file.
- **`default.json`** (repo root) is the shared Renovate preset every app repo's `renovate.json` extends (`github>tn4consulting/mfe-pot-platform`) — groups `react`, `react-dom`, and `@tn4consulting/shared-ui-scds-core` into one coordinated bump (`rangeStrategy: pin`), the federation-shared singletons every app repo must keep in lockstep (see "Federation-sharing policy" below; `@gcds-core/components` was removed from this group when GCDS was removed from the family entirely). This repo is the designated home for cross-repo shared config generally (this preset, `platform-versions.json`); a short-lived separate `mfe-pot-renovate` repo and the `mfe-pot` meta repo were both considered and rejected for that role.
- **`pnpm.overrides` in every repo's root `package.json` pins `listr2`** to one exact version, unchanged by the migration — confirmed it's not an Angular-specific pin (job-bank, always React, carries the identical override), just a transitive dependency version that happened to be grouped alongside Angular's coordinated-bump rule in the old Renovate preset.
- BFF request/response contracts stay lightweight (hand-written TS interfaces in each `libs/<domain>/data-access`, not generated from a schema) — a deliberate, acceptable scope limit for this PoT, not an oversight.

**A real gotcha discovered building the publish pipeline**: a `libs/shared/*` package's `dist/` folder must never exist *inside that lib's own directory* except transiently during an actual `npm publish`. Once it does (e.g. from manually running `nx build <lib>`, which — per its `tsconfig.lib.json` — outputs there so a *published* package's `package.json` "main" field resolves correctly), Nx's jest resolver starts preferring that plain-`tsc`-compiled output over the TS source for any *other* project's test that imports the package, which can break in surprising ways depending on what the lib's own build step does or doesn't inline (this bit hardest, historically, for an Angular component library whose `templateUrl`/`styleUrl` a plain `tsc` build never inlines the way `jest-preset-angular`'s source transform did — no longer a live concern now that no lib in this repo has that shape, but the general resolver-preference mechanism is still real for any published lib). Fixed at the tooling level: `tools/scripts/publish-shared-lib.mjs` builds via the normal `nx run shared-<name>:build` target (which outputs to the shared, out-of-the-way `dist/out-tsc/libs/shared/<name>/src/` tree, safe because nothing resolves a package there), copies only that lib's own output slice into `libs/shared/<name>/dist` for the moment `npm publish` needs it, then deletes it again. If `nx test` ever starts failing on a shared lib with an odd "can't resolve" error right after a manual `nx build` of that same lib, check for a stray `libs/shared/*/dist` folder before assuming the code is wrong.

### Components live in the app, only data-access stays a separate library
Each app's real components/business logic live directly under `apps/<name>/src/app/*.tsx` — a flat set of components, not a separate `libs/<name>/feature-*` Nx library the way the pre-migration Angular apps organized things. This shape came from job-bank (the original React reference implementation, which needed to work both federated into the shell *and* standalone on the real-world Job Bank site) and every other app adopted it identically once converted, for consistency and because a React remote's whole "every remote is self-configuring" design (see "Federation" below) doesn't benefit from an extra library boundary the way Angular's DI-driven feature libraries did. The one library that *does* stay separate per app is `libs/<name>/data-access` (the `<Domain>ApiClient` interface + `Http<Domain>ApiClient` implementation) — genuinely reusable in isolation (e.g. by tests) in a way the components themselves aren't.

Components depend on cross-cutting concerns (identity, locale, cross-remote widgets) via **plain React hooks and Context**, never a host's concrete implementation directly — `useLocale()`/`useTranslations()` (`shared-i18n`), `getStoredSession()`/`onSessionChange()` (`shared-auth/core`), and the generic keyed widget-loader Context in `shared-federation-runtime` (`useWidgetLoader(widgetId)`) are all plain importable hooks, not something a host has to wire in per-consumer the way Angular's `InjectionToken` providers required. This is a genuine simplification the migration bought, not just a mechanical port — see "Federation" below for the fuller story.

### Federation
- **Native Federation** (`@softarc/native-federation` — the framework-agnostic core; the family stopped depending on the `@angular-architects/native-federation` wrapper entirely once the last Angular app converted), not Webpack Module Federation — esbuild-based. Nx does not have first-class Native Federation support today (its built-in MF tooling is webpack-based), so every app's `build`/`serve` targets are hand-written scripts (`apps/<name>/build/build.mjs`/`serve.mjs`) calling `@softarc/native-federation-esbuild`'s `runEsBuildBuilder` for the federation build plus a plain `esbuild.build()`/`esbuild.context()` call for the app's own standalone entry bundle — not an Nx/Angular executor.
- Remote discovery goes through a `RemoteRegistryProvider` abstraction, not a static file read directly — entries carry name, URL, route prefix, and version. Three implementations: Strapi-backed (local dev — edit a "Remote" entry in Strapi and the shell picks it up next load, no rebuild/restart), static baked-JSON (for a hosted/no-CMS deployment), in-memory stub (tests). `apps/shell/src/main.tsx` itself inlines the Strapi-first-with-fallback logic rather than using this abstraction directly (see the bare-specifier gotcha), falling back to `runtimeConfig.remotes` instead of a static JSON provider once Kubernetes hosting lands (see "Hosting: Kubernetes + Helm" below). On a version mismatch, the shell warns and loads anyway — this is a demo tool, not a production compatibility gate.
- Two federation patterns are proven: (a) each MFE exposes a routed `./Component` the shell mounts via `RemoteRouteHost` (React.lazy + Suspense — see below), and (b) three standalone cross-remote widgets: `dashboard` exposes `./PaymentHistoryWidget` (rendered inline by `life-events` — still true), `job-bank` exposes `./JobApplicationsWidget` and `employment-insurance` exposes `./EiReportingStatusWidget`. The latter two used to also be rendered inline by `dashboard`'s own overview, but that embed was dropped (`docs/msca-screenshots/dashboard.png` has no job-applications/EI-reporting-status tile on the dashboard page) — each now renders directly on its own owning app's page instead (`job-bank`'s/`employment-insurance`'s own `App.tsx`), and the federation expose + the shell-mediated loader Contexts stay in place unconsumed, proving the pattern without a live consumer today.
- **A routed remote's exported `App` mounts directly inside the shell's own React tree — no second React root.** `RemoteRouteHost` (`shared-federation-runtime`) resolves the remote's `./Component` export via `React.lazy(() => loadRemoteModule(...))`, wrapped in `<Suspense>` plus a class-based error boundary (`RemoteErrorBoundary` — only an error boundary, not a try/catch, can catch a lazily-loaded component's load/render failure). A failed remote/widget degrades to an inline "temporarily unavailable" message in its own route/section, never a crashed shell. This replaced the pre-migration Angular version, which needed an injected `REACT_MOUNTER` function and a manual `unmount()` on destroy specifically because Angular's `ViewContainerRef` couldn't host a React tree directly — a React host has no such boundary to cross, so that whole mounting layer is gone, not ported.
- **Cross-remote widget composition is host-mediated, not remote-to-remote.** A remote calling `loadRemoteModule` on *another* remote is tempting but doesn't work: `@softarc/native-federation-orchestrator`'s `loadRemoteModule` awaits an in-memory promise that only the calling bundle's own `initFederation()` resolves. Since we deliberately don't share the native-federation packages themselves (see federation.config.mjs comments — sharing them breaks the *host's* own bootstrap import, a chicken-and-egg failure), every remote bundles its own disconnected copy of that runtime, so a nested `loadRemoteModule` call from within a remote just hangs forever with no error. The fix: the **shell** (which always has a working federation runtime) loads the cross-remote widget itself and hands the resolved component down to the consuming remote via a React Context the shell provides above `RemoteRouteHost` in `apps/shell/src/app/routes.tsx` — see `WidgetRegistryContext`/`useWidgetLoader(widgetId)` in `shared-federation-runtime` (`2.0.0+`; a single generic keyed registry, not one hand-written Context+hook pair per widget type as it was through `1.x` — see that package's own `CLAUDE.md`/changelog for why, added alongside the multi-life-event generalization). Because the remote mounts inside the *same* React tree as the host (not a second root) and `shared-federation-runtime` is a federation-shared singleton (every app resolves the identical Context object instance), a `<WidgetRegistryContext.Provider>` the shell renders anywhere above `RemoteRouteHost` is visible to the remote's own `useContext` call once it loads — no explicit prop-threading through `RemoteRouteHost` required.
- **Every remote is fully self-configuring — there is no `./RemoteProviders` equivalent.** The pre-migration Angular version had each remote export its own `REMOTE_PROVIDERS` (HTTP client, interceptors, its Transloco scope), which the shell applied via a child `EnvironmentInjector` before mounting. A React remote has no DI tree for a host to populate: each exposed component fetches its own runtime config and builds its own API client on mount instead (see any app's `App.tsx`), the same way job-bank — the original React reference implementation — always worked. This is a genuine simplification the migration bought, not just a mechanical port.
- `federation-runtime` wraps every dynamic remote import in explicit failure handling — a failed remote/widget degrades just that route/widget, not the whole shell.
- **A plain library must never import `@softarc/native-federation`/`-orchestrator` directly** — it can silently get its own bundled copy of the package, separate from the one `main.tsx` initializes. Native federation's builder only keeps the package external (pointing at the one shared dev-optimized/prod-shared copy) for the entry points and exposed modules it explicitly manages; an ordinary library chunk that transitively imports it falls back to esbuild's default "bundle everything not marked external" behavior, inlining a second copy with its own disconnected module-scoped state. Symptom: `loadRemoteModule` calls made through that copy hang forever — no error, no rejection, because that copy's internal `federationPromise` is only ever resolved by *its own* `initFederation()` call, which never happens. Fix: the library takes `loadRemoteModule` via `useRemoteModuleLoader()` (a Context hook, `shared-federation-runtime`) instead of importing the orchestrator package itself; only `apps/<name>/src/main.tsx` provides the real function.
- **The identical "must stay external" rule applies to a host's own hand-written `esbuild.build()`/`.context()` call for its non-federation-managed entry bundle (`main.tsx`/`bootstrap.tsx`), not just to plain libraries — and it's easy to only remember it for `react`/`react-dom`.** Confirmed the hard way in `mfe-pot-msca-shell`'s `build.mjs`/`serve.mjs`: the `external` array correctly listed `react`/`react-dom`/`react-dom/client` (needed so the host's own React instance is the same one a federated remote's bundle resolves to — omitting them throws "invalid hook call" the moment a remote's component, rendered directly inside this same tree, calls a hook) but omitted `@tn4consulting/shared-federation-runtime`. The federation build (`runEsBuildBuilder`) already produces a correct standalone shared chunk + import-map entry for that package; without also marking it external in the *separate* plain-esbuild call for `main.tsx`, that second bundle silently inlined its own second, disconnected copy of the widget-loader Context objects. `routes.tsx`'s widget-loader Context provider (`<JobApplicationsWidgetLoaderContext.Provider>` at the time this was found — since generalized into `<WidgetRegistryContext.Provider>`, same identity-crossing concern) wrote into that inlined copy's `_currentValue`; a consuming remote's widget-loader hook (resolving through the correctly-shared chunk instead) read the *other* copy's default (`undefined`) — no error, no console output, just every cross-remote widget silently rendering its "unavailable" fallback forever. Any package a host's own entry bundle needs Context-identity-sharing with (not just React itself) needs the same `external` treatment.
- **A minified shared react.js chunk crashes at runtime — every app's `build.mjs` deliberately passes `dev: true` to `runEsBuildBuilder`'s federation-build step even in a production build, accepting a cosmetic `-dev.js` filename suffix on just the shared vendor chunks in exchange.** Found live, on a real `kind` deployment: `TypeError: i is not a function` at `shared-federation-runtime`'s own module-eval time (it calls `createContext()` synchronously at the top level), crashing the whole app to a blank page. Root cause traced to the shared `react.js` chunk itself: every *named* import from `'react'` (`import { useState } from 'react'`) resolves to `undefined` at runtime once that chunk is minified, while the *default* export (`import React from 'react'; React.useState`) stays correctly populated — confirmed directly by comparing an unminified build's `react.js` (a real ~74KB populated CJS module body) against the minified one (~16KB, the named-export-extraction guard-check scaffolding present but nothing before it in the file to populate what it's checking). This is esbuild's minifier tree-shaking away the CJS module body `@chialab/esbuild-plugin-commonjs`'s named-export extraction depends on (triggered by `needsCommonJsPlugin: true`, see above) — a genuine bug in that minify+CJS-shim interaction, not anything app-specific, and it's **universal**: reproduced independently against job-bank's own production build too, not just shell's. It was silently broken in every app since each one's own React conversion, because every phase's live-verification throughout this whole migration used `nx serve` (dev) — never a real `nx build` + browser check — until a live `kind` deployment finally exercised the actual production build path. `node_modules/.../native-federation-esbuild/.../node-modules-bundler.js` hardcodes `minify: !dev` for these shared chunks specifically, with no independent minify-only control, which is why the fix reuses the `dev` flag rather than something more surgical — judged lower-risk than patching a third-party dependency for what's otherwise a cosmetic filename concern. Each app's own standalone bundle (the separate, later `esbuild.build()` call in the same `build.mjs`) is unaffected and stays fully minified.

### Federation-sharing policy
Default to **not** marking a library as a federation "shared" singleton. Every shared entry re-couples the apps' deploy/version schedules — the opposite of the independence goal — so it's only worth it for dependencies that are large, stable, and low-churn enough that the coupling cost is clearly repaid, *or* whose whole purpose is identity (not just behavior) crossing a federation boundary. Today that bar is met by **`react`/`react-dom`** (large/stable/low-churn), **`@tn4consulting/shared-ui-scds-core`** (large/stable, plus every remote renders these custom elements directly with no wrapper to isolate the sharing behind), and **`@tn4consulting/shared-federation-runtime`** (not large or low-churn at all, but its React Context objects need the exact same object identity in every app that provides or consumes a widget-loader Context, or `useContext` silently resolves to `undefined` with no error — see "Federation" above). It is explicitly *not* met by feature/business-logic code or anything with active churn — which is why the mock auth session and active locale cross remote boundaries as a small versioned DTO + broadcast event instead of a shared singleton. Weigh any future sharing candidate against this same bar.

### Design System (SCDS)
Every app consumes `@tn4consulting/shared-ui-scds-core`'s custom elements **directly** via JSX. SCDS is a self-contained, in-house design system — GCDS (`@gcds-core/components`, the GC Design System) has been removed from the family entirely; `libs/shared/ui-scds-core` was rebuilt from scratch as its own Stencil component library rather than a wrapper around GCDS (see this repo's git history — "Rebuild shared-ui-scds-core as a self-contained design system, remove GCDS" — if you need the old GCDS-wrapper shape). Each app declares a small hand-written `scds-elements.d.ts` (`declare global { namespace JSX { interface IntrinsicElements { 'scds-header': ... } } }`) typing only the elements/props it actually renders. **Only the two host apps render `scds-header`/`scds-sidebar`/`scds-footer`** — remotes render content only, never their own header/footer/nav.

- **SCDS custom elements are safely idempotent to double-register on their own** (each component checks `customElements.get()` before calling `define()`, so a second federated bundle's `customElements.define()` call is simply skipped, not a crash) — the Angular-era `NG0912` "component ID generation collision" concern doesn't exist for React at all, since there's no per-bundle wrapper *class* to collide (a plain custom element has no such identity). `@tn4consulting/shared-ui-scds-core` stays a federation-shared singleton anyway (see "Federation-sharing policy" above) mainly to keep behavior consistent if versions ever drifted across remotes — whichever bundle's `define()` call runs first is the one every `<scds-*>` element on the page actually gets upgraded with, version-shared or not, so an un-shared version mismatch would silently skew toward whichever remote loaded first rather than crash.
- **A component with a named slot only projects content passed to that exact slot name** (e.g. `scds-header`'s `account`/`toggle`/`skip-to-nav` slots). Content without an explicit `slot="..."` attribute is silently dropped by the browser, not an error — if an SCDS component's projected content isn't appearing, check the slot name against the component's source (`libs/shared/ui-scds-core/src/components/<name>/<name>.tsx`, or the compiled `node_modules/@tn4consulting/shared-ui-scds-core/dist/components/<name>.js`) before assuming it's a bug elsewhere.
- **An SCDS prop's real DOM attribute name is kebab-case, confirmed directly from the compiled Stencil metadata** (`node_modules/@tn4consulting/shared-ui-scds-core/dist/components/<name>.js` — every real `@Prop()` has an `"attribute": "..."` field), and for most props a plain JSX attribute (`skip-to-href="..."`) is enough — React sets it via the custom element's real property setter when one exists on the upgraded element's prototype, which Stencil always defines. **One confirmed exception**: `scds-multi-column-list`'s `items`/`columns` props are non-primitive (arrays/objects) — Stencil never reflects those to/from a DOM attribute at all, so they must be set imperatively as JS properties (`el.items = [...]`) after creating the element with `document.createElement`, not via JSX (see job-bank's `FeatureSearch.tsx` for the pattern). A plain-string prop that's optional and has `reflect: false` (e.g. `scds-card`'s `description`/`tone`) *will* show up correctly via a JSX attribute — confirmed by inspecting the live shadow DOM, not just `outerHTML`/`getAttribute()`, which won't show a `reflect: false` prop's value even though it rendered correctly.

### Security: defense in depth
The shell's sign-in is a real authorization-code + PKCE flow against `apps/mock-idp` (a genuine OIDC-shaped mock IdP: an `/authorize` page, one-time codes, RS256-signed JWTs, a JWKS endpoint) — not a one-click stub. `apps/shell/src/app/LoginPage.tsx` builds PKCE params (`auth-flight.ts` — S256 challenge with a `plain` fallback for non-secure-context deployments) and full-page-redirects to `mock-idp`'s `/authorize`; `AuthCallbackPage.tsx` reads the returned `?code&state`, validates the CSRF state against the stored flight, and `POST`s `mock-idp`'s `/token` endpoint to exchange the code for a real signed JWT, then calls `storeSession()`. Every BFF independently verifies that JWT against `mock-idp`'s JWKS endpoint via `libs/shared/auth-server`'s bearer-token middleware — not a shared secret, a real signature check.

The resulting session crosses remote boundaries the same way active locale does — `sessionStorage` + a `window` `CustomEvent` broadcast (`libs/shared/auth/src/lib/session-sync.ts`), not a shared federation singleton — because it's exactly the same kind of small, versioned, per-session state the sharing policy above already covers. **Each app enforces its own security** — never assume "the shell let me navigate here, so I'm authorized." The shell has real sub-routes, so it guards them with a `RequireSession` wrapper component (`apps/shell/src/app/RequireSession.tsx`, React Router) on `/dashboard` etc., redirecting to `/` when there's no session. Remotes have no internal routing in this PoT (each exposes one component), so each one's own `App` component checks its own claim directly (`hasClaim(getStoredSession(), CLAIM_X)`) and renders a "sign in required" state instead of its content when absent — same principle as a route guard, different mechanism, since there's no sub-route to guard. Verified concretely: a remote hit directly at its own dev-server origin, with no shell and no session, independently blocks its own content — it doesn't rely on the shell having stopped it. `libs/shared/auth/core` (session model, `session-sync`, `createMockSession`/mock-login helpers, claim constants) is bundled normally by each app, not a federation singleton, since it's stateless logic; the package's root export is functionally identical to `/core` today (the Angular-only `requireSessionGuard` that used to live there was deleted once shell converted to React Router) but every app repo still imports the `/core` subpath explicitly, so it stays as a distinct entry point rather than being collapsed away for zero benefit.

### Independent testability
Every app must be buildable, serveable, and testable entirely on its own, using stub implementations of whatever it's normally handed (auth token, locale, registry entries) — without the shell or any sibling remote running. The composed `mfe-e2e` Playwright suite proves the apps work together; each app's own standalone test target proves it hasn't grown a hidden runtime dependency on the shell. Treat a regression here as a real regression, not an acceptable cost.

`apps/mfe-e2e` is a plain hand-written Nx project (`@nx/playwright:configuration`'s generator only *adds* Playwright to an existing project, so this one — a standalone composed suite with no single "host" app — was created by hand instead) covering routed federation across all 4 remotes, cross-remote widget embedding, the language-switch broadcast, the BFF-backed golden path (apply for a job, apply for EI, confirm it lands in the dashboard overview), and `@axe-core/playwright` WCAG 2.2 AA scans on every route (currently zero violations). `playwright.config.ts`'s `webServer` array starts all 9 local processes (5 frontends + 4 BFFs) so the suite is self-contained in CI, with `reuseExistingServer` so local iteration can attach to an already-running stack instead of restarting everything. Three non-obvious things had to be right for this to work:
- **`webServer.command` runs from the config file's own directory, not the workspace root** — `nx run <project>:serve` needs to resolve workspace-relative paths (`tsconfig.base.json` etc.), so every entry sets `cwd` to the actual repo root explicitly.
- **Starting many `nx run` processes concurrently contends for the single shared Nx daemon hard enough to crash it** (SQLite task-history writes racing) — each spawned process sets `NX_DAEMON=false` so it runs standalone instead of coordinating through that daemon.
- **Every BFF has a plain, stateless `GET /health`** used for Playwright's readiness check specifically because the natural-looking alternative — probing a real domain endpoint like `/api/claims?applicantSub=...` — depends on mutable in-memory state (a claim that may or may not exist yet) and intermittently reported "not ready" depending on what earlier test/demo runs had left behind.

**Known gap**: the 4 BFFs hold in-memory state with no reset endpoint yet, so repeated local/CI runs accumulate applications and claims rather than starting from zero — the golden-path e2e test deliberately uses loose assertions (`.first()`, existence checks) rather than exact counts for this reason. A `pnpm demo:reset` command (already called for in the demo narrative below) would fix this the same way it fixes repeatable live demos.

### Minimize cross-MFE shared state
Independence is the point of this architecture. Shared runtime state is a liability to justify, not a default. Today it's limited to: the React/SCDS/shared-federation-runtime singletons, the auth token DTO, and the active locale. Any proposal to share more goes through the sharing-policy bar above.

### Backends: BFF pattern, where it earns its keep
`job-bank` and `employment-insurance` each have their own dedicated backend (`job-bank-bff` on :3001, `employment-insurance-bff` on :3002) — realistic shape, and it pays off the "Job Bank must be reusable outside this shell" requirement (a standalone consumer needs a real API, not client-side mock state). `dashboard-bff` (:3004) composes MSCA-D's cross-benefit overview by calling those two services over real HTTP for the `activeApplications`/`jobApplications`/`eiReportingStatus` tiles — not by importing another domain's in-memory state — plus its own local `payments`/`correspondence` data, the same in-memory-stub pattern the other two BFFs use for their own domains.

**Known, accepted tradeoff**: "tell us once" data (payments, correspondence) used to be served by its own `client-profile-service` (:3003) specifically so it was one shared source across all three domain BFFs, not a disconnected per-remote copy — an in-memory lib scoped to just one BFF would silently give each independently-built remote its own copy of "the profile," which is exactly what happened when that service was removed and its data folded into `dashboard-bff`'s own `data.ts` (no Helm chart ever existed for `client-profile-service`, so its one caller 502'd in any real deployment — simpler to delete it than to keep patching around the missing chart). `job-bank-bff`/`employment-insurance-bff` never had access to this data and still don't; the "tell us once" demo-narrative beat (`../TODO.md`) is flagged there as needing a redesign before it can be built.

All four are plain Express/TypeScript apps (`@nx/node:application`, `framework=express`), each with an `export function createApp(): Express` (in `app.ts`) separate from `main.ts`'s `.listen()` call, so tests exercise the real Express app via `supertest` without a live socket. **Their inferred lint target is named `eslint:lint`, not `lint`** — the `@nx/node` generator doesn't add an explicit `lint` target the way every frontend app/lib's `project.json` does (those declare it manually); run `nx run <bff>:eslint:lint` directly, or note that a plain `nx run-many --target=lint` silently skips these four projects rather than failing.

`dashboard-bff`'s fan-out (`overview.ts`) has an explicit partial-failure contract, `fetchJson()`'s `UpstreamResult<T>` (`{status:'ok', data} | {status:'unavailable'}`): a slow/failed/non-2xx upstream degrades only its own tile, never the whole response. A citizen with no EI claim on file gets a 404 from `employment-insurance-bff` — that's handled as a distinct case (`{status:'ok', data: null}`), not `unavailable`, since "no claim yet" is a legitimate state, not a service failure. Verified live by killing `job-bank-bff` (active-applications/job-applications tiles degrade, payments/correspondence — local, no upstream — keep rendering real data) and separately killing `employment-insurance-bff` (the eiReportingStatus tile alone degrades).

Each frontend talks to its backend through a thin `<Domain>ApiClient` interface + `Http<Domain>ApiClient` implementation, in a dedicated `libs/<domain>/data-access` library (mirrors the `ContentClient`/`RemoteRegistryProvider` pattern). Each app's `App.tsx` constructs the concrete `Http<Domain>ApiClient` itself (a plain `new HttpXApiClient(runtimeConfig.xBffBaseUrl)` in a `useEffect`, once its own fetched runtime config resolves — see "Hosting: Kubernetes + Helm" below) and passes it down as a prop to whichever component needs it; components take the interface type, never construct the concrete class themselves, for the same reason they take locale/identity via hooks rather than importing a concrete implementation (see "Components live in the app" above) — just a constructor-injected value via props now, not a DI token.

**The cross-remote payment-history widget is fully self-configuring, same as every other converted widget** — it fetches its own runtime config and builds its own `HttpPaymentHistoryApiClient` on mount, whether rendered by `dashboard`'s own overview or embedded in `life-events` via `useWidgetLoader('payment-history')`. This replaced the pre-migration Angular version's `component`+`providers` pairing (`PaymentHistoryWidgetLoader` resolving to `Promise<{ component, providers }>`, with the shell also loading dashboard's `./RemoteProviders` and `life-events` applying those providers via `createEnvironmentInjector` before `createComponent()`) — a React widget has no DI tree for a host to populate, so there's nothing left to pair; see "Federation" above.

`dashboard`/MSCA-D and `life-events` don't get their own dedicated backends — there's no distinct bounded context there that justifies one. Not every MFE needs a BFF; add one only where it earns its keep.

### i18n
UI chrome text uses **`shared-i18n`'s `useTranslations(assetBaseUrl, locale)` hook** (runtime-switchable, per-MFE translation loading — required since remotes are independently deployed and can't share a compile-time i18n scheme), replacing the pre-migration Angular version's Transloco integration. Each component calls `const { t } = useTranslations(assetBaseUrl, locale)`, computing its own `assetBaseUrl` the same `new URL('.', import.meta.url)` way every remote's asset/runtime-config fetches already do (see the esbuild gotcha above). `t(key, params?)` supports `{{param}}`-style interpolation (`interpolate.ts`) — the one real consumer today is `employment-insurance`'s `reportingStatus.nextReportDue` (`{date, days}`, `date` pre-formatted via `Intl.DateTimeFormat` before interpolation, not a raw ISO string). Active locale itself comes from `useLocale()` (`shared-i18n`, built on `shared-locale-sync`'s framework-agnostic `getStoredLocale`/`onLocaleChange`/`broadcastLocaleChange`) — a `localStorage` value + `window` `CustomEvent` broadcast, deliberately not a federation singleton, per the sharing policy above.

Page content is bilingual and CMS-driven through the `ContentClient` abstraction (`libs/shared/content-client`). Three implementations, same interface: `StrapiContentClient` (real EN/FR entries from the live CMS), `StaticContentClient` (fetches this app's own baked `public/assets/content-fallback/<locale>.json`, the same URL-per-locale shape `shared-i18n`'s `useTranslations` already uses for chrome JSON), and `FallbackContentClient` (wraps the two — Strapi as primary, `StaticContentClient` backing it up). `createContentClient(strapiBaseUrl, assetBaseUrl)` in each app's own `content-client.ts` picks the shape: no `strapiBaseUrl` configured → `StaticContentClient` directly; configured → `FallbackContentClient(StrapiContentClient, StaticContentClient)`, so a live CMS outage or a not-yet-seeded key degrades to bilingual fallback content instead of surfacing English-only text or an error. `FallbackContentClient.getPageContents` tries the primary first; if it throws, every requested key falls back; if it succeeds but is missing some keys, only those are backfilled from the fallback, keeping Strapi's own data authoritative for the rest. Every app's `App.tsx` renders one CMS-driven intro block (`<app>.intro` key) above its own components, re-fetched via a `useEffect` keyed on `locale` whenever the cross-remote active-locale broadcast fires (`ContentClient`, unlike the hook-based chrome text above, isn't reactive by default) — `content-client.ts`/`createContentClient` is the same small pattern in every app repo, job-bank's `apps/job-bank/src/app/content-client.ts` was the original reference example. Each app's own `public/assets/content-fallback/{en,fr}.json` is the single source of truth for that app's content — it already existed for the client-side fallback case above; Strapi's own seeding (`tools/cms/strapi/src/content-seed.ts`) fetches these same files over HTTP from each app's own Ingress host and upserts them into `page-content`, rather than reading a hardcoded array baked into Strapi's own image. This is a deliberate ownership choice: a content-only change in one app no longer requires a `mfe-pot-platform` PR or a Strapi image rebuild. See "Local CMS / federation directory: Strapi" below for the fetch/seed mechanism itself.

**Feature-level static text (headings, table/form labels, status/alert text) is CMS-driven too**, not just each app's own intro block — `ContentClient.getPageContents(keys, locale)` (a batch variant alongside `getPageContent`, since a component like the payment-history widget needs ~7 keys at once and N separate round-trips doesn't scale) fetches a component's whole label set in one request. Each app has a small `usePageContents(contentClient, keys, locale)` hook (React equivalent of `App.tsx`'s own single-key fetch-and-resubscribe pattern) wrapping this. `contentClient` is threaded down as a prop from `App.tsx` alongside `apiClient` for components that already receive props that way; a component exposed as a standalone federated widget with no host-provided props (`PaymentHistory.tsx`, `ReportingStatus.tsx`, `JobApplicationsList.tsx`) self-constructs its own `contentClient` via `createContentClient(runtimeConfig.strapiBaseUrl, assetBaseUrl)` inside its own runtime-config-loading effect, same as it already does for its API client. Templated CMS strings (`Claim {id}`, `Status: {status}.`) use `fillTemplate` (also in `shared-content-client`) — a `{key}`-style substitution helper, deliberately distinct from `shared-i18n`'s Transloco-era `{{key}}` syntax used for app-chrome text, since CMS content and chrome i18n stay separate systems. **No component keeps its own hardcoded-English fallback anymore** — `label(key)` is just `content[key]?.title ?? key` (the raw key is a last-resort that should never actually surface, since `ContentClient` itself now guarantees bilingual coverage down to the baked JSON). One consequence worth knowing when writing tests: content resolution is always asynchronous, even the fallback path (a `fetch`, or a mocked `Promise`) — a synchronous `getByText`/`getByRole` query run immediately after `render()` can catch a component mid-load, still showing the raw key. Use `findByText`/`findByRole` (or wrap attribute assertions in `waitFor`) for anything whose text comes from `ContentClient`, the same way `App.spec.tsx`'s intro-content test already had to.

Verified end to end: switching language via the shell's toggle updates the shell's own nav chrome *and* an independently-loaded remote's chrome simultaneously, each fetching its own `en.json`/`fr.json` from its own origin off the single broadcast event — the same proof point as the pre-migration Angular version, just via a hook re-render instead of a re-provided `TranslocoService` instance. The Angular-era DI gotchas this section used to document (`TranslocoService`'s `providedIn: 'root'` singleton leaking across a child `EnvironmentInjector`, `APP_INITIALIZER` never firing for one) have no React equivalent — a hook has no per-injector identity to leak across a federation boundary in the first place.

`dashboard`'s payment-history widget (`PaymentHistory.tsx`, embedded live in `life-events`) now sources its heading/table labels/status text from the CMS (`dashboard.payment-history.*` keys via `ContentClient.getPageContents`, re-fetched on cross-remote locale change via `useLocale`) — previously static English mock text, closed alongside the same fix in `job-bank`'s and `employment-insurance`'s own feature components (`job-bank.*`/`employment-insurance.*` keys). **Remaining, narrower gap**: currency formatting (`$${amount.toFixed(2)}`) and the underlying payment/benefit *values themselves* (test data, by design) are still locale-naive — full data/currency/date bilingual fidelity beyond labels is a later demo-narrative beat (see "the bilingual switch is demoed as a real flex" in the plan).

### Local CMS / federation directory: Strapi
`tools/cms/strapi` is a real Strapi 5 (TypeScript, SQLite) project, run locally via its own Helm chart (`charts/strapi`) deployed to the local `kind` cluster with `pnpm deploy:local` (`tools/deploy-local.sh`) — see "Hosting: Kubernetes + Helm" below for the general build/kind-load/helm-upgrade loop this follows. Two content types, defined as code (not created by hand in the admin UI) under `tools/cms/strapi/src/api/`:
- **`page-content`** — bilingual (Strapi i18n plugin, `en`/`fr` locales) page content, read via `ContentClient`.
- **`remote`** — the federation directory (name, url, routePrefix, version), read via `RemoteRegistryProvider` (`libs/shared/remote-registry`). Editing an entry in the Strapi admin and reloading the shell picks up the change with no rebuild — this is the actual "live directory server" capability, not just a config file.

Seeding is a **bootstrap script** (`tools/cms/strapi/src/index.ts`), not a `strapi export` archive — it's idempotent (checks before creating) and also grants the Public role read access to both content types and creates the `fr` locale, so `pnpm deploy:local` produces a complete, working environment on every fresh pod with zero manual admin-panel steps. Local-dev-only dummy secrets (`APP_KEYS` etc.) are committed directly in `charts/strapi/values.yaml` for the same reason — never reuse them for anything real.

`page-content` seeding itself (`tools/cms/strapi/src/content-seed.ts`) fetches each content-owning app's own `assets/content-fallback/{en,fr}.json` over HTTP rather than reading a hardcoded array — ownership stays with the app that owns the content, not this repo. Fetch base URLs for the 4 federated remotes reuse the same `REMOTE_<NAME>_URL` env vars `REMOTES` seeds from (stripped of `/remoteEntry.json`), rather than adding 4 redundant vars; the two host apps (`job-bank-shell`, `msca-shell`) each get one dedicated `CONTENT_<NAME>_URL` var since they're not federated remotes and have no `REMOTE_*_URL` entry of their own. `bootstrap()` calls this once synchronously (a fast path for an already-warm cluster), but the real self-heal path is a Strapi cron task (`config/cron-tasks.ts`, wired explicitly via `config/server.ts`'s `cron: { enabled: true, tasks }` — Strapi's config loader does *not* auto-merge a `config/cron-tasks.ts` file into `server.cron.tasks` by filename convention, confirmed by tracing `@strapi/core`'s own source) re-running the same idempotent fetch+seed on an interval. This matters because `deploy-local.sh`/`deploy-eks.sh` deploy Strapi before any content-owning app exists on a from-scratch run — the synchronous bootstrap pass fails quietly (logged, not thrown) every time on a genuinely fresh cluster, and the cron task is what actually converges once each app becomes reachable, without needing either deploy script to change.

Each seeded `remote.url` is read from a `REMOTE_<NAME>_URL` env var, falling back to the `nx serve` localhost dev port (`http://localhost:4201/remoteEntry.json` etc.) if unset — **not** hardcoded, despite looking like static seed data. This matters once Strapi is actually deployed (see `charts/strapi` below): a *reachable-but-wrong* directory is worse than an unreachable one, since `resolveFederationManifest()`/`ContentClient` in each app only fall back to their own configured default when Strapi itself is unavailable, not when its data is stale.

The shell reads the registry via `RemoteRegistryProvider` in `apps/shell/src/main.tsx` (inlined logic, not the shared lib — see the bare-specifier gotcha above), with a 3s timeout and fallback to `runtimeConfig.remotes` if Strapi is slow/unreachable — see "Hosting: Kubernetes + Helm" below for what populates that value (dev defaults locally, a container-injected map once deployed). This replaced the old baked `federation.manifest.json` file entirely.

**`charts/strapi`** deploys this as its own Helm release, live-validated on the local `kind` cluster alongside all 5 apps (see "Hosting: Kubernetes + Helm" below for the general pattern this deliberately doesn't reuse). Exposed at Ingress host `cms.mfe-pot.local` — "cms", not "strapi", since the latter is an implementation detail no citizen-facing or demo-facing hostname should say. `charts/strapi/values.yaml` sets each `REMOTE_<NAME>_URL` to the real sibling app's Ingress hostname, and `mfe-pot-msca-shell`/`mfe-pot-dashboard-mfe`'s own chart `values.yaml` `strapiBaseUrl` fields point at the same `http://cms.mfe-pot.local` — confirmed end to end by curling both apps' live `env.js` plus Strapi's `/api/remotes`/`/api/page-contents` through the Ingress. `tools/deploy-local.sh` (`pnpm deploy:local`) is the one-command build/kind-load/helm-upgrade loop for it, matching each app repo's own `deploy:local` script.

### Hosting: Kubernetes + Helm (pattern proven for all 5 apps + platform infra; local kind CI done, AWS EKS Terraform written, not yet applied)
Firebase Hosting has been retired (`firebase.json`, `.firebaserc`, and the `build-hosted` copy-step target are gone) in favor of **Kubernetes — AWS EKS in the cloud, `kind` locally — deployed via Helm**. Every app repo's `.github/workflows/ci.yml` now has a `kind-validation` stage (build image(s), spin up an ephemeral kind cluster, `helm install`, curl the Ingress host) wired in and green — that part is done, not still open. **The cloud target changed from the originally-planned Azure (AKS/ACR) to AWS EKS in 2026-08** — a deliberate pivot (no technical reason, Azure account access was unmanageable), not something the earlier planning docs anticipated; see `../docs/plans/20260808-1500-mfe-pot-aws-eks-terraform.md` for the full design, decisions, and current status. Terraform for the AWS side (`infra/terraform/{bootstrap,foundation,cluster}`, in this repo) is written and `terraform validate`d against real module versions, split into a persistent layer (ECR image repos, Route 53 zone, GitHub OIDC/IAM) and an ephemeral layer (VPC, EKS cluster, node group, ingress-nginx/external-dns/cert-manager) so the expensive bits can be `apply`'d before a demo and `destroy`'d after — not yet actually applied to a real AWS account (blocked on working AWS credentials in the environment this was authored in). Every app repo plus this repo's own `charts/mock-idp`/`charts/strapi` now also has a `values-eks.yaml` + Ingress TLS block + a `deploy-eks` CI job (gated on push to `main` and on the demo cluster actually existing) alongside the existing kind path — kind's own `values-kind.yaml`/CI behavior is untouched by any of this.

**Renaming an app repo/image needs a `terraform apply` on `foundation`, or CI silently loses ECR push access.** Confirmed live 2026-08-09, renaming `mfe-pot-employment-life-events-mfe` → `mfe-pot-life-events-mfe`: `ecr_repository_names` in `infra/terraform/foundation/variables.tf` was updated in the same rename commit, but nobody re-ran `terraform apply` against the real AWS account — so the GitHub Actions IAM policy (derived `for_each` off that same list) still only granted push access to the old repo name. The renamed repo's `deploy-eks` job failed at the image-push step (`ecr:InitiateLayerUpload ... not authorized`), which left its EKS release stuck on its last successful pre-rename deploy — old Helm release, old Ingress hostname, old image — while the renamed app's *consumers* (`mfe-pot-msca-shell`'s `values-eks.yaml`, Strapi's seeded remote directory) had already switched to the new hostname, which had no DNS/Ingress at all yet. Net effect: a citizen-facing "temporarily unavailable" federation-load failure with no red CI on the *consuming* app's own pipeline — the actual break was a stuck `deploy-eks` job in a sibling repo. Fix was a manual `terraform apply` in `infra/terraform/foundation` (creates the new ECR repo + updates the IAM policy resource list) followed by re-running the renamed repo's `deploy-eks` job. Any rename that touches `ecr_repository_names` needs that `terraform apply` as an explicit follow-up step — it is not something the rename PR's own CI catches, since `terraform validate`/`plan` never run against real AWS credentials in CI today.

**Runtime config, not build-time — done.** One container image per app gets built once and promoted across environments unchanged; environment-specific values (BFF URLs, Strapi URL, the remotes map) come from a Helm-chart-supplied ConfigMap injected at pod startup instead of Angular's old `fileReplacements`/`environment.prod.ts` swap:
- **`@tn4consulting/shared-runtime-config`** (`libs/shared/runtime-config`) exports `getRuntimeConfig<T>(devDefaults: T): T`, which merges `window.__mfePotEnv` over dev-time defaults. Each app has its own `src/runtime-config.ts` calling this with just the fields it needs (e.g. `apps/dashboard/src/runtime-config.ts` has `strapiBaseUrl`, `dashboardBffBaseUrl`) and imports `loadRuntimeConfig`/`runtimeConfig` from it wherever a component needs a base URL (`App.tsx`, and any self-configuring widget like `PaymentHistory.tsx`). The old `environments/` directories and `fileReplacements` build-config blocks are deleted everywhere they existed.
- **`apps/shell/src/main.tsx` can't use the shared package** — same bare-specifier-from-`main.tsx` constraint as `shared-remote-registry` (see the gotcha above) — so it inlines its own small `{ ...devDefaults, ...window.__mfePotEnv }` merge instead. Its config shape is `{ strapiBaseUrl, remotes }`, where `remotes` (a `Record<name, remoteEntryUrl>`) is what the old baked `federation.manifest.json`/`.prod.json` swap-file pair used to hold. `resolveFederationManifest()` still tries Strapi first with the existing 3s timeout, falling back to `runtimeConfig.remotes` instead of the old bundled JSON file.
- **`window.__mfePotEnv` needs an actual place to be set before the app boots**: every frontend that reads runtime config (`shell`, `dashboard`, `job-bank`, `employment-insurance`, `life-events`) has a `public/env.js` (`window.__mfePotEnv = {};` — a harmless no-op default for `nx serve` and for the image's baked-in placeholder) loaded via a plain blocking `<script src="env.js"></script>` in `index.html`'s `<head>`, placed before the deferred `<script type="module-shim" src="main.js">` entry tag so it always runs first regardless of build output ordering. In a container, `tools/docker/frontend-entrypoint.sh` overwrites this exact file at startup with the real values.
- Verified end to end: full `nx run-many -t lint,test,build --all` green across all 27 projects, plus a live smoke test (`nx serve shell` + `nx serve dashboard`) confirming the dev-default fallback path behaves identically to the old `environment.ts` values.

**Docker images, Helm library charts, and kind validation — proven for job-bank first, then repeated for the other 4.**
- **Frontend image** (`Dockerfile` in each app repo's `apps/<app>/`, same shape for every frontend): multi-stage — builder stage runs `pnpm install` + `nx build <app> --configuration=production`, runtime stage is plain `nginx:alpine` serving `dist/apps/<app>/browser`. `tools/docker/nginx.conf` (same file, copied into each app repo) sets the same CORS/no-cache/immutable-cache headers the old `firebase.json` did per app. `tools/docker/frontend-entrypoint.sh` is dropped into nginx's `/docker-entrypoint.d/` (the official image auto-runs every script there before starting nginx, so no custom `ENTRYPOINT` override is needed) and writes whatever `MFE_POT_ENV_JSON` env var it finds into `env.js`, defaulting to `{}` if unset. Shell and life-events have no BFF, so their repos have only this one Dockerfile.
- **BFF image** (`Dockerfile` in each owning app repo's `apps/<bff>/` — `job-bank-bff`, `employment-insurance-bff`, `dashboard-bff`): multi-stage — builder stage `nx build <bff>`, runtime stage plain `node:22-alpine` copying `dist/apps/<bff>` and the **full workspace `node_modules`**, not a pruned subset, since each extracted repo is now its own single-package workspace with a real top-level `package.json` — the pruning problem this used to have (no per-project `package.json` to scope from) resolved itself once extraction happened, per the plan. **A real gotcha caught here**: the BFF's `main.ts` binds `process.env.HOST ?? 'localhost'` (fine for local dev), but inside a container `localhost` is the container's own loopback interface — a Pod's Service can never reach a process only listening there despite it looking healthy from inside its own container. Every BFF image sets `ENV HOST=0.0.0.0` to fix this; this is an image/chart-level fix, not a code change, since `HOST` is already an env var the app already reads.
- **Helm library charts** (`charts/mfe-frontend-lib`, `charts/mfe-backend-lib`, live in this repo permanently) hold reusable Deployment/Service/ConfigMap named-templates (`type: library` in `Chart.yaml`, never installed directly) — `mfe-frontend-lib.deployment`/`.service`/`.configmap` and the `mfe-backend-lib` equivalents. Each has a `README.md` documenting its values contract. **Ingress is deliberately not part of either library chart** — the original design sketch put it there, but a single Ingress needs both the frontend's and backend's Service names together to express the path-based split below, which doesn't fit a per-component library template cleanly; each application chart hand-writes its own single `templates/ingress.yaml` instead.
- **Each app's application chart** now lives in that app's own repo (`charts/<app>` — job-bank's was the template the other 4 followed): `Chart.yaml` declares `dependencies` on both library charts via local `file://../../../mfe-pot-platform/charts/...` sibling-checkout-relative paths (becomes a packaged/OCI reference once the library charts are pushed to a registry), `values.yaml` holds real defaults, `values-kind.yaml` overrides `image.pullPolicy: Never` and `image.tag: kind` for locally-built images with no registry round-trip, and `templates/` is just one-line `{{ include "mfe-frontend-lib.xxx" . }}` / `{{ include "mfe-backend-lib.xxx" . }}` files plus a hand-written `ingress.yaml`. Shell and life-events' charts only depend on `mfe-frontend-lib` (no BFF).
- **BFFs are exposed under their own frontend's hostname via an Ingress path rule**, confirmed working exactly as designed for every BFF: each BFF's own Express routes already carry the `/api` prefix internally (`/api/jobs`, `/api/claims`, etc.), so the Ingress path rule is a plain prefix match with no rewrite needed, and each frontend's `runtime-config.ts` dev default becomes e.g. `jobBankBffBaseUrl: "/api"` in the chart's `values.yaml` — a same-origin relative path, not a second hostname. `dashboard-bff` is the one exception worth knowing: it calls the other two BFFs over real cross-Helm-release **in-cluster Kubernetes Service DNS** (`<service>.default.svc.cluster.local`), not through Ingress, since that traffic is server-to-server, not browser-to-server.
- **Validated live on a local `kind` cluster** for every app (`tools/k8s/kind-config.yaml`, port-mapping 80/443 to the host and labelling the node `ingress-ready=true` per kind's own Ingress guide): `kind create cluster` (note: this environment's Docker daemon reports `Cgroup Version: 1`, and kind's current default node image, built for k8s 1.36, failed `kubeadm init` against it outright — pin an older node image, e.g. `kindest/node:v1.27.3`, which starts cleanly on a cgroup-v1 host) → install the kind-flavoured `ingress-nginx` static manifest → `docker build` each app's image(s) → `kind load docker-image` (no registry needed) → `helm install <app> ./charts/<app> -f values.yaml -f values-kind.yaml` → pods reach Ready → `curl -H "Host: <app>.mfe-pot.local" http://localhost/` returns the real `index.html` (200, `env.js` script tag present) and `/env.js` returns the real ConfigMap-injected values, not the image's `{}` placeholder. dashboard's validation was the strongest proof of the cross-service design specifically: with job-bank and employment-insurance already deployed in the same cluster, `dashboard-bff`'s `/api/overview` returned real `"ok"` data for every tile — the partial-failure contract working across real Helm releases, not just in a single process.

**The kind-based CI validation stage is now wired into all 5 app repos'** `.github/workflows/ci.yml`: lint/test/build, then build the image(s), spin up an ephemeral `kind` cluster (checking out this repo as a sibling directory for the library charts' `file://` dependency and `tools/k8s/kind-config.yaml` — a public-repo checkout, no extra secret needed), `helm install` that app's own chart, and curl the Ingress-routed hostname to confirm it serves. Each workflow deploys only its own app-pair, not the full 5-app topology, so cross-service smoke checks (`dashboard-bff`'s fan-out) deliberately assert reachability rather than depend on sibling BFFs being deployed in the same job.

**Not yet built**: Phase 2 — rewiring `apps/mfe-e2e`'s `playwright.config.ts` `webServer` array, which today starts nothing (`client-profile-service`, the one thing it used to start, has been removed), to point at each sibling app repo's checkout so the composed suite covers all 5 apps again (this is the one place a *real* multi-app deployment, not just each repo's own CI, would actually exercise cross-app behavior); pushing the two library charts to a registry as OCI artifacts (still referenced by local `file://`/sibling-checkout paths — this is independent of the AWS pivot below and isn't blocking it, since the same sibling-checkout trick works fine in a GitHub Actions runner too); actually running `terraform apply` against a real AWS account and landing the first live `deploy-eks` CI run (see the Hosting section above and `../docs/plans/20260808-1500-mfe-pot-aws-eks-terraform.md` for the AWS EKS design that superseded the AKS/ACR plan this bullet used to describe). Full history of the original polyrepo split in the meta repo's `../docs/plans/20260801-1935-mfe-pot-polyrepo-split-and-k8s-hosting.md`.

### Observability: OpenTelemetry (traces + metrics)
Closes the `../TODO.md` "Observability" item: a single citizen action (e.g. `dashboard-bff`'s fan-out to `job-bank-bff`/`employment-insurance-bff`) can now be followed across service boundaries by one trace ID. Traces and metrics only — no logs signal yet, since no BFF has a structured logger (winston/pino) to attach trace context to; a genuinely new addition, not an upgrade of anything pre-existing.

**Client-impact guarantee: an unavailable or unreachable OTel collector can never affect a citizen-facing request.** Both `initNodeObservability` and `initBrowserObservability` wrap their own SDK setup in try/catch and log-and-continue rather than throw — telemetry is strictly best-effort. This is on top of (not a replacement for) what's already inherently true of the OTel SDKs' own design: exporters run on an async batch timer fully decoupled from real request/response handling, so a collector being down just means a batch export silently fails/retries in the background, never something that blocks or throws into application code. Verified live, not just asserted: scaling `otel-collector` to 0 replicas on `kind` and hitting `dashboard-bff`'s real fan-out repeatedly showed no latency change and zero errors.

**Two new shared packages** (`libs/shared/observability-server`, `libs/shared/observability`), mirroring the `shared-auth`/`shared-auth-server` client/server split:
- **`@tn4consulting/shared-observability-server`** — Node SDK bootstrap for the 3 BFFs (`@opentelemetry/sdk-node` + `auto-instrumentations-node`, OTLP/HTTP export). Its `./register` subpath is a side-effect module every BFF's `main.ts` imports as the literal first line, before `./app` — `require-in-the-middle`'s module-patching hook has to install before `express`/`http`/`undici` are first required, which only holds because every BFF's esbuild target compiles to `format: ["cjs"]` with `bundle: false` (real, source-ordered `require()` calls against un-inlined `node_modules`). Instrumenting `undici` (not just `http`) matters specifically because `dashboard-bff`'s fan-out (`overview.ts`) calls the other two BFFs via native `fetch`, not `http.request`. No-ops entirely if `OTEL_EXPORTER_OTLP_ENDPOINT` is unset (plain `nx serve`), same dev-default posture as `shared-session-cache`'s `REDIS_URL`-unset fallback; throws at startup if the endpoint is set but `OTEL_SERVICE_NAME` isn't, rather than letting BFFs silently misattribute spans to each other.
- **`@tn4consulting/shared-observability`** — browser Web SDK bootstrap (`@opentelemetry/sdk-trace-web` + `instrumentation-fetch`/`instrumentation-document-load`, OTLP/HTTP export). **Deliberately not a federation-shared singleton** — see the dedicated subsection below, this is a real precedent-setting decision worth reading before adding any other cross-cutting browser concern.

**Deliberately not federation-shared — read this before touching any frontend repo's `federation.config.mjs`.** The "Federation-sharing policy" bar above is "large/stable/low-churn, or its whole purpose is identity crossing a federation boundary." The OTel Web SDK doesn't need that: cross-service trace linkage (browser → BFF → downstream BFF) happens over the **W3C `traceparent` HTTP header**, not JS object identity — the same mechanism that already makes BFF-to-BFF propagation "just work" with zero JS sharing. Each app (both shells, all 4 remotes) bundles and runs its own independent `WebTracerProvider`/`MeterProvider` pair. Two consequences worth knowing:
- **`initBrowserObservability` never calls the global `WebTracerProvider.register()` form** — with every federated app on one page bundling its own copy of this package, global (`globalThis`-based) registration would let whichever bundle happens to load first silently win and mis-attribute every other app's spans to its own `service.name`, a load-order-dependent bug with zero errors. It uses `registerInstrumentations({ tracerProvider, meterProvider, instrumentations })` instead, which never touches `globalThis`.
- **`propagateTraceHeaderCorsUrls` is not optional for any app with a BFF.** `FetchInstrumentation` doesn't attach `traceparent` to cross-origin requests by default, and a federated remote's BFF call is cross-origin from the browser's point of view even when embedded in a shell — `fetchRuntimeConfig` resolves a remote's own BFF base URL against *its own* origin, not the host's (see `job-bank-mfe`'s `runtime-config.ts`). Without it, spans still generate locally but silently never carry `traceparent` to the BFF — the same silent-failure shape this file already documents for the federation `external`-array gotcha. Each remote's `runtime-config.ts` sets it to a regex matching its **own** hostname prefix only (e.g. `/^https?:\/\/job-bank-mfe\./`, deliberately not anchored to `.mfe-pot.local` or `.aws.tn4consulting.com` specifically, since the same bundle runs on both kind and EKS); the 2 shells and `life-events-mfe` have no BFF of their own, so it's omitted there.

**Per-app wiring point differs by role** (confirmed by reading the actual entry-point files, not assumed): the 2 host apps (`msca-shell`, `job-bank-shell`) call `initBrowserObservability` from `bootstrap.tsx` (their one real entry point — hosts are never federated into anything else). A remote's own `main.tsx`/`bootstrap.tsx` never runs when federated into a shell (the shell imports the remote's exposed `./Component` directly, bypassing them entirely) — so each of the 4 remotes wires it once, inside its own `runtime-config.ts`'s `loadRuntimeConfig`, the one function every current and future exposed entry point (`App.tsx`, and any standalone widget like `PaymentHistory.tsx`) already funnels through. `initBrowserObservability` is idempotent (module-level guard) specifically because of this — `dashboard-mfe` exposes both `./Component` and `./PaymentHistoryWidget`, so calling its one wiring point twice in a session is a real, expected case, not a hypothetical.

**Shared infrastructure** (`mfe-pot-platform/charts/otel-collector`, `charts/tempo`, `charts/prometheus`, `charts/grafana`) — four bare-upstream-image charts modeled on `charts/session-cache`'s shape (no library-chart dependency, no PersistentVolume — traces/metrics are resettable demo data, not durable storage, same posture as Redis having no persistence), each installed once, independently, alongside `session-cache`/`strapi`/`mock-idp`:
- **`otel-collector`** (`otel/opentelemetry-collector-contrib`) — the single OTLP/HTTP ingestion point (port 4318) every BFF (in-cluster Service DNS) and every frontend (this chart's own Ingress host, browser-reachable — unlike Redis, the collector needs to be reachable from the citizen's actual browser, not just from Pods) exports to. Fans traces out to Tempo; its own `prometheus` exporter at `:8889` also exists for whatever app-level metrics genuinely get emitted (Node runtime/event-loop/GC metrics, confirmed live — see below), scraped by Prometheus via the same pull model.
- **`tempo`**/**`prometheus`** — trace/metrics storage, cluster-internal only (no Ingress, no `values-eks.yaml` at all — identical on kind and EKS, same reasoning as `session-cache`). **RED metrics (request rate/error rate/duration) are deliberately derived from spans, not from each BFF's own HTTP auto-instrumentation** — `charts/tempo`'s `metrics_generator` (span-metrics processor, enabled via `overrides.defaults.metrics_generator.processors`) turns every ingested span into `traces_spanmetrics_*` series, `remote_write`d into Prometheus (`--web.enable-remote-write-receiver`, `charts/prometheus/templates/deployment.yaml`). Chosen because deriving RED from spans (one signal, proven reliable end to end) is simpler than depending on each language/framework's own metrics-emission support, which varies.
- **`grafana`** — the actual "way to view the data collected": a provisioned "BFF RED metrics" dashboard (`charts/grafana/templates/dashboards-configmap.yaml`, request rate/error rate/p50+p95 latency per `service`, built on `traces_spanmetrics_*`) plus Explore against both Tempo and Prometheus. Ingress-exposed at `grafana.mfe-pot.local`/`grafana.aws.tn4consulting.com`, same `<name>.mfe-pot.local` scheme `cms`/`mock-idp` already use.

**A real, live-confirmed Node ESM-vs-CJS gotcha, worth knowing before writing any other verification/debug script against a BFF**: testing `shared-observability-server` with a plain `.mjs` script (dynamic `import('http')`) produced traces for outgoing (`fetch`/undici) calls but **silently no spans or metrics at all** for the incoming `http.createServer` side — not a metrics-only gap, no server-side span in the trace either. Root cause, confirmed by direct source inspection: `@opentelemetry/instrumentation-http`'s core-module patch relies on `require-in-the-middle`, which hooks CJS's `Module._load` — ESM's own module loader for built-ins doesn't reliably go through that path. Re-testing the identical scenario as a plain `.cjs` script (`require('http')`) produced correct spans **and** metrics for both directions immediately. **This does not affect any real BFF** — every one of the 3 BFFs' esbuild target compiles to `format: ["cjs"]` (see `./register`'s own doc comment above), so this gotcha is purely a hazard for anyone writing an ad hoc `.mjs` verification/debug script against this package, not a limitation of the package itself.

**Env var wiring reuses existing mechanisms, no Helm template changes anywhere**: `mfe-backend-lib`'s flat `backend.env` ConfigMap gets `OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_SERVICE_NAME` (in-cluster Service DNS, identical on kind/EKS, so only in the base `values.yaml`, same as `REDIS_URL`); `mfe-frontend-lib`'s JSON-blob ConfigMap gets `otelExporterOtlpEndpoint` in `frontend.runtimeConfig` (browser-reachable — the kind-shaped default lives in the base `values.yaml`, `values-eks.yaml` overrides it to the AWS hostname, same split `strapiBaseUrl` already uses).

**Both `otel-collector` and `grafana` needed a `values-eks.yaml` + TLS-enabled `templates/ingress.yaml`** (copying `charts/strapi`'s conditional-TLS shape verbatim) since the AWS EKS pivot (see "Hosting" above) landed mid-implementation of this feature — `tempo`/`prometheus` didn't, since they're cluster-internal only. `mfe-pot-platform/tools/deploy-local.sh` deploys all 4 right after `session-cache`, before Strapi; `mfe-pot/tools/deploy-eks.sh`'s Step 3 does the same directly (no CI job — like `session-cache`, none of the 4 have a Dockerfile of their own to push to ECR).

Lint with React-aware TypeScript rules — `typescript-eslint` + `eslint-plugin-react`/`eslint-plugin-react-hooks`/`eslint-plugin-jsx-a11y`, not just generic TypeScript lint — across every app/lib with `.tsx` files. **Follow lint rules; don't suppress them to get past a check.** A failing rule means fix the code, or, if the rule is genuinely wrong for a case, change the rule deliberately and say why — not an inline disable comment and move on.
