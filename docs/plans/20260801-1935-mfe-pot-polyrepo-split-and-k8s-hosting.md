**Decisions already confirmed with the user (via AskUserQuestion):**
1. **Local dev model: independent sibling clones**, no git submodules — tied together with a VSCode multi-root `.code-workspace` file. 2. **Shared libs → versioned npm packages published to GitHub Packages.** This is also the direct answer to "how do I enforce strong contracts": semver + published TypeScript types become the enforced boundary — a breaking change requires a major version bump, and a consumer that hasn't updated simply fails to build.

## Strong contracts strategy (the user's explicit question)

1. **Versioned npm packages with published `.d.ts` for everything in `libs/shared/*`**, published to GitHub Packages under the `@tn4consulting` scope (GitHub Packages requires the npm scope to match the owning org — not an arbitrary `@mfe-pot` name). The TS compiler enforces the contract on every consumer at build time; a major version bump is the explicit "I changed the contract" signal.
2. **A new `libs/shared/federation-config` package** holding the Native Federation `shared`/`skip`/`features` block that is *currently hand-copied verbatim into all 5 apps'* `federation.config.mjs` (confirmed identical via exploration — `@angular/core`, `@angular/common`, `@angular/platform-browser`, `@angular/router`, `@angular/forms`, `rxjs`, `@gcds-core/components`, `@gcds-core/components-angular`, all `{singleton:true, strictVersion:true, requiredVersion:'auto'}`). Today that duplication is low-risk because one PR can fix all 5 at once; once split, 5 independent repos hand-copying the same singleton config is exactly how federation singleton-version mismatches happen silently. Each app's `federation.config.mjs` imports this instead and only supplies its own `exposes`.
3. **Fix the one real module-boundary violation before splitting anything**: `apps/shell/src/app/app.routes.ts` imports `PAYMENT_HISTORY_WIDGET_LOADER` from `employment-life-events-feature-guided-journey` (confirmed via exploration — this is a `libs/employment-life-events/*` lib, and shell has a compile-time dependency on it). Once shell and employment-life-events are separate repos this can't compile. Fix: move `payment-history-widget-loader.token.ts` into `libs/shared/federation-runtime` (already the home of `RemoteRouteHost`/`REMOTE_MODULE_LOADER` — the same "cross-remote loading needs a DI token, not a direct import" pattern already established there). Both shell's repo and employment-life-events' repo then depend on the same published `@tn4consulting/shared-federation-runtime` package.
4. **Tighten `@nx/enforce-module-boundaries` before the split**, while it's still cheap to fix violations in one PR. Exploration confirmed the current depConstraint is `sourceTag: '*' → onlyDependOnLibsWithTags: ['*']` — wide open, which is *why* the shell violation above wasn't caught. Replace with real constraints using the tags already present (`type:app`, `type:shared`, `scope:<domain>`): apps can depend on `type:shared` and same-`scope` libs only; `type:shared` libs can't depend on anything scoped; no lib may depend on a `type:app`. Every currently-passing app should still pass; this is a safety net, not a rewrite.
5. **A version-alignment check, run periodically against the deployed apps** (a small script/workflow in the platform repo — not urgent for the first pass, but call out as the natural verification once everything is deployed): fetch each remote's live `remoteEntry.json` (Native Federation's own manifest already lists every shared package's exact resolved `version`) and each BFF's `/health`, and assert they agree with a single checked-in "platform versions" reference (Angular/RxJS/GCDS/Node pins). This turns "did someone silently drift a shared singleton version" from an NG0203-class production mystery into an automated, visible check — and doubles as a nice "show the seams" demo moment.
6. **BFF response contracts stay lightweight for now**: `benefit-aggregation-bff` already declares its own local `JobApplication`/`EiClaim`/`Payment`/`CorrespondenceItem` interfaces describing what it expects from the other BFFs (duck-typed, not shared types) — acceptable for this PoT's scale. Flag as an explicit, deliberate non-goal for this pass (each BFF publishing generated types/OpenAPI would be the production-grade next step) rather than silently leaving it ambiguous.

## Hosting: Kubernetes + Helm (replaces Firebase)

Phase 0 is done and verified (full lint/test/build sweep green, live smoke test clean — see CLAUDE.md's "Monorepo → per-app repos" and "Strong contracts" sections for what shipped). Before doing Phase 1's app extraction, this hosting redesign needs to land first, so each new repo's CI is written once, correctly, against Kubernetes/Helm rather than Firebase and then rewritten later.

**Decisions confirmed with the user (via AskUserQuestion):**
1. **Runtime config, not build-time**: one container image per app, built once. Environment-specific values (BFF URLs, which remotes to load, Strapi URL) come from a ConfigMap injected at pod startup, not from Angular's `fileReplacements`/`environment.prod.ts` swap. This is what actually lets the same image promote from kind -> AKS unchanged, which is the whole point of containerizing. **DONE — see Status above.**
2. **5 hostnames via Ingress, one per app-pair** (e.g. `shell.mfe-pot.example.com`, `dashboard.mfe-pot.example.com`), mirroring today's 5 Firebase Hosting sites. Preserves the "these are genuinely independent origins" proof this project is built around for the *federated frontends*, which is what that proof is actually about.
3. **Azure Container Registry** for both container images and Helm charts (ACR supports OCI Helm chart storage) — natural fit since AKS is the deploy target, no cross-cloud pull credentials needed. Confirmed this doesn't conflict with also using kind locally (see below) — kind local dev doesn't round-trip through ACR at all.
4. **kind** for local Kubernetes, replacing `docker-compose.yml` and minikube (only just installed, not a switching cost). `kind load docker-image <tag>` needs no per-shell environment state (unlike minikube's `eval $(minikube docker-env)`), and kind's port mappings are set at cluster-creation time (a `kind-config.yaml`) so Ingress just hits `localhost:80`/`443` directly -- no standing tunnel process needed. Ingress controller setup is one `kubectl apply` of the kind-specific ingress-nginx manifest. **`nx serve <app>` remains the fast local dev loop** -- kind is for testing the containerized/deployed shape (and running Strapi + BFFs together more realistically), not a replacement for hot-reload iteration.

**Sequencing: kind first, Azure second.** Neither AKS nor ACR exist yet (confirmed). Get the whole pattern -- runtime config, Docker images, both library charts, every app's own chart, Ingress routing -- working and validated end to end against kind before provisioning any Azure resource or touching the "push to ACR / deploy to AKS" half of any CI workflow. This de-risks the Azure work (which becomes "point the already-proven charts at a different registry/cluster") instead of debugging the whole stack for the first time against real cloud infrastructure. Concretely: Phase 1's per-app CI workflow only gets a kind-based validation stage for now (see below); the ACR-push/AKS-deploy stage is a follow-up pass added once Azure is provisioned.

**BFFs are exposed under their own frontend's hostname via a path, not a separate hostname** -- e.g. `dashboard.mfe-pot.example.com/` routes to the dashboard frontend Service, `dashboard.mfe-pot.example.com/api` routes to `benefit-aggregation-bff`'s Service, both declared as two path rules in the same Ingress resource. This keeps the real hostname count at **5** (matching the frontends 1:1), and makes frontend-to-its-own-BFF calls same-origin -- the `cors()` middleware already in every BFF becomes unnecessary for this specific call path (same-origin requests don't trigger CORS checks) but stays harmless, so no code needs to change.

### Helm charts — library charts done, job-bank's application chart done as the template

**One chart per app repo is the actual deployable unit** — each app and its co-located BFF deploy and version *together, as a single Helm release*, independent of every other app. This is the point: `helm upgrade --install dashboard ./charts/dashboard` deploys/updates/rolls back the dashboard frontend + `benefit-aggregation-bff` pair as one unit, with zero coupling to job-bank's or shell's releases.

To avoid hand-copying the same Deployment/Service YAML shape 5+ times, two Helm **library charts** (Helm's mechanism for shared, non-installable template logic — the direct analogue of the `shared-federation-config` npm package) live in the platform repo (`charts/mfe-frontend-lib`, `charts/mfe-backend-lib`, `type: library` in `Chart.yaml`) and will get pushed to ACR as OCI artifacts once a registry exists — referenced via local `file://../` paths for now. Each holds a `.configmap`/`.deployment`/`.service` named template plus a `README.md` documenting its values contract (`.Values.frontend.*` / `.Values.backend.*`).

**Design refinement made while actually building this (differs from the original sketch)**: Ingress ended up **not** part of either library chart. A single Ingress needs both the frontend's and backend's Service names together to express the path-based BFF split (`/` -> frontend, `/api` -> backend) — that doesn't fit a per-component library template cleanly. Instead, each application chart hand-writes its own single `templates/ingress.yaml` (see `charts/job-bank/templates/ingress.yaml` for the reference shape — turned out simpler than expected, since job-bank-bff's own routes already carry the `/api` prefix internally, so no `rewrite-target` annotation is needed, just a plain prefix match).
